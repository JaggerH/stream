# Stream 定时任务 — 挂之前先想清楚三件事

这份 skill 回答三个问题，顺序不能换：

1. **这条任务跟谁抢东西？**（互斥）
2. **它该什么时候跑？**（排期）
3. **它轮不上的时候，是等，还是这一班不跑？**（迟到语义）

绝大多数事故来自第 1 问没答就去答第 2 问——**用错开时间点来防撞**。那是能用，但它把一个
硬约束藏进了一串看起来只是"随便排的时间"里：下一个人在同一个点上加一条任务，界面不会拦，
跑挂了也没人说得出为什么。

---

## 第 1 步：互斥判定 —— **给资源起名字，不是给任务分类**

**互斥的单位是"被抢的那个东西"，不是任务的业务类别。**「A股任务」不是一个互斥组——
A 股的财报和 A 股的日线抢同一座数据桥，那是因为桥只有一座，不是因为它们都姓 A 股。

照这四问答，答完就有结论：

### 1.1 这条任务跑起来会独占什么？

在本仓里，"只有一份、同时只能有一个人用"的东西就这几类：

| 资源 | 谁在抢 | 怎么认出来 |
|---|---|---|
| **一座外部数据桥的 worker** | 所有走同一座桥的采集任务 | 采集器 import 了同一个 bridge 模块（如 Cockpit 的 `collectors/jq.py`），桥后面是单 worker |
| **一份登录态浏览器标签** | 所有要在同一个站点上点东西的任务 | 走 ext-cdp / 同一个 `configRef` 账号 |
| **一个库文件的写锁** | 写同一个 `.duckdb` / `.db` 的任务 | 落盘路径相同 |
| **一个第三方账号的速率配额** | 共用同一把 key 的任务 | 同一个 `configRef` |
| **（没有）** | 纯读、纯计算、各写各的文件 | —— |

答"没有" → **这条任务不需要互斥**，到此为止，别给它设互斥组。

### 1.2 还有别的任务也要那个东西吗？

没有 → 同样不需要互斥组。**一个人独享的东西不需要排队。**

### 1.3 有 → 互斥组的名字就是那个资源的名字

不是市场名、不是数据集名、不是"重要任务组"。**名字要能让下一个人一眼看出自己该不该进来。**
`jq-bridge` 是好名字（我要不要走这座桥？看一眼采集器就知道）；`cn-data` 是坏名字
（"我这条算不算 cn-data"永远说不清，于是有人进来有人不进来）。

### 1.4 一条任务同时抢两样东西怎么办？

**这是已知的表达不全**：互斥组只有一格，抢两样就只能保住一样。两条路：

- 拆任务——通常这条任务本来就该拆（一条任务同时打两座桥，本身就是把两个源钉在一起了）；
- 保不住的那一样，在任务描述里写清楚，并靠时间点兜。**但要在描述里说这是兜底，不是设计。**

---

## 第 2 步：排期 —— 时间点只服从源的发布节奏

第 1 步做对了，时间点就**只需要回答一个问题**：这个源什么时候有新数据？

- 收盘后结算的 → 等结算完；
- 上午发布的 → 上午跑，别攒到晚上；
- 周频的（比如周五发上周二的持仓）→ 一周跑一次，别天天跑；
- 月频、季频的 → 一周跑一次都算勤快。

**反模式：一个时间点同时扛"发布节奏"和"别跟谁撞"两件事。** 出现这种情况说明第 1 步没做，
回去做第 1 步。

**一张表一条任务，不是一个数据集一条。** 把节奏不同的源合成一条，只能迁就最慢的那个：
快的赶不上（周更的财报在披露季最多滞后 5 天），慢的天天白抓。

---

## 第 3 步：迟到语义 —— 判据是"迟到之后还算不算数"

轮不上的时候有两种处置，选哪种**不看这条任务重不重要**，只问一句：

> 这次执行晚一小时跑，还是它本来要做的那件事吗？

- **是** → **排队**。补数据、导出、发布都属于这类。晚了照样有价值。
- **否** → **这一班不跑，并且报红**。凡是有外部时间窗的动作——申购/打新、竞价前的报盘、
  有截止时间的提交——迟到执行不是"晚了一点"，是**做了一件错事**。宁可这一班空掉、
  在账本里红一次让人看见。

**默认是排队。** 只有你能说出那个外部时间窗是什么，才选跳过。

## 已实测的坑（每一条都在活体上撞到过）

### `serial: true` 不是"这条任务自己不叠"

它一次做两件事，而这两件事本该分开：

1. 同一条任务不叠着跑（存活即拒）；
2. **进一个全局单槽队列**——所有 `serial` 任务共用这一个槽，一次只能跑一个。

第 2 件是绝大多数人不知道的。后果是**过度串行**：一条能跑 6 小时的补数任务，会把同样标了
`serial` 的、秒级的、有硬时间窗的任务堵在后面。**给一条任务标 `serial` 之前，先问它是不是
真的要和所有其他 `serial` 任务互斥。**

### 排队不吃超时，所以"排队"是便宜的

`timeoutMs` 是在**子进程 spawn 那一刻**才起表的。在队列里等 3 小时不会被算进超时。
所以"等"这个选项没有隐藏代价——不要因为怕超时而去选跳过。

### cron 是 6 段（含秒），不是 5 段

给 5 段不报错，"分"会被当成"秒"——一条本该每天跑一次的任务变成每分钟跑一次。
写路由会拦，但**手写脚本直接改库不会**。

### 改一条任务要把整行发回去

写接口只有 upsert 一条。只发想改的那一格，**其余的格会被抹掉**（表现不是报错，是任务
悄悄丢了 cwd / env 然后跑挂）。正确做法：先读出整行，改那一格，整行发回去。

### 新建的任务不会倒补"最近那一班"

任务行记着"它从何时起存在"，自愈只补这之后的槽。周六 10:00 建一条工作日 09:45 的任务，
不会下一分钟就把周五那一班跑掉。**这是要的行为**，别去掉它——对下单类任务，倒补是真会出事的。

### 后端是常驻进程，改了代码它不会自己知道

改完调度相关的代码，**必须重启后端再验**（`systemctl --user restart stream-back.service`）。
拿旧进程的响应当验证结果，是这一块最常见的假绿。

### 写脚本批量改任务：先探针，后删除

批量重排的正确次序是——先写一条、**回读确认新字段真的存下来了**，再写其余的，
全部回读校验通过之后**才**删旧任务。跳过探针那一步，遇到后端版本不对的情况会是
"HTTP 全 200、界面上什么都没变"，是最难发现的一种失败。

## 挂一条新任务的清单

```
[ ] 它独占什么？没有 → 不设互斥组；有 → 组名 = 资源名（第 1 步）
[ ] 已经有别的任务在抢同一个东西吗？没有 → 还是不设
[ ] 时间点只按源的发布节奏定，没有一个点是为了"避开谁"（第 2 步）
[ ] 迟到之后还算不算数？不算 → 设成跳过并报红（第 3 步）
[ ] 一张表 / 一个源一条任务，没有把两个节奏合成一条
[ ] cron 写了 6 段
[ ] 改存量任务：读整行 → 改一格 → 发整行
[ ] 改了代码：重启后端再验，别信旧进程
```
