# 桌面这一面（`kind:'desktop'`）

驱动原生桌面客户端，不走浏览器。**两条词汇，按应用有没有控件树选**：

| | 用什么指一个东西 | 什么时候用 |
|---|---|---|
| **a11y** | `query`（role / name），点击走 native invoke | 应用有控件树（Telegram 这类 Qt/Win32） |
| **像素** | `see`（屏幕上的这段文字 / 这个图标），点击走坐标 | 自绘应用（微信），控件树里什么都没有 |

**跨平台分叉写在 groundings 里，不复制整份 recipe。** 三种差异三种写法，别混：

- **名字不同** → `app.process`（和 `window` 步骤的 `match.process`）写一组候选
  （`["Weixin.exe", "微信", "WeChat"]`）：Windows 与 mac 上同一个应用的进程名不同（mac 还跟界面
  语言走），运行时按「屏上有哪个」落成一个再交给 agent（`concretizeApp`）。
- **动作不同** → 那一步挂 `groundings[]`，每条是一份完整的动作 body 加一个 `on`
  （`platform` / `app` / `lang`，没写的键 = 不限）；顶层 body 就是通用那一条。运行时按 agent 报的
  事实（`WindowInfo.platform` / `appVersion`）挑，逐条试，每条试完都跑顶层 `expect`。
  样板是 `wechat-send` 的「等候选弹层」：通用 body 等 Windows 那个标题「Weixin」的独立弹层窗口，
  `darwin` 那条等标题 `<无标题 AXDialog>` 的窗口——mac 上候选也是独立弹层，只是没有标题。
  **mac agent 给无标题的 AXDialog / AXFloatingWindow / AXSheet 合成标题 `<无标题 <subrole>>`**，
  `window.match.title` 照字面写；别的无标题窗口照旧不进清单。判「候选画在哪」别看主窗截图——
  弹层是另一个窗口，主窗截图里永远看不见它；用 `see-probe <进程> "<无标题 AXDialog>"` 直接读那扇窗。
- **判据不同 → 判据不分叉。** `expect` / `require` / `else` / `optional` / `blind` / `label` /
  `intent` / `skipIf` 只住顶层，写进 grounding 是格式错误、装载即拒。判据与落地方式无关是这套
  东西能安全重填的前提：换了办法点进去，检查的还是同一件事。`see.region` 是例外——它可以经
  `see.area` 走区域分叉（判据的文字仍不分叉，分叉的只是那块屏在哪）。

**平台事实从 agent 来，不看 `process.platform`**——后端在 WSL、agent 在 Windows 那种组合下后端
自己的平台就是错的答案。老版本 agent 不报平台时只剩通用 body。

**`on.app` 永远和 `on.platform` 一起写。** 两个平台报的版本格式不是一回事：Windows 报 exe 的文件
版本（四段，`4.0.6.36`），mac 报 bundle 的 `CFBundleShortVersionString`（`4.0.6`）。裸写一个区间，
它在另一个平台上会落在你意料之外的一侧。区间只认 `>= > <= < =` 与裸版本号，空格分隔即 AND
（`>=4.0 <4.1`）；`^` / `~` / `||` 装载期当语法错拒掉。

**判据看的那一块屏两平台不同 → 用具名区域，不取并集。** 判据的文字（"正文出现在气泡区"）通用；那一块在窗口里
占哪儿是落地事实，走顶层 `areas` + `see.area`（`docs/PACKAGE.md` §2.4 "Named areas"）。`wechat-send` 的输入区
Windows 从 0.72 起、mac 从 0.60 起——各写各的，两边都收紧。**别再写并集 region**：判据是回车前唯一的闸，
一个放松的 region 和一个没有闸长得一样。区域一块都选不中时整趟以 `no-grounding@area:<名字>` 停在发出任何
输入之前——照事实补一条 `on` 相符的区域 grounding，不是去放松判据。

**drift 原因里出现 `no-grounding@<步骤 label>`** = 这一步的所有候选落地方式都试过了、没有一条让
`expect` 兑现。那句话里带着试过的清单和当前事实（平台、应用版本）——照着事实补一条 `on` 与它相符
的 grounding，而不是去放松判据。步骤的 `label` 因此必填且全份唯一：它是本机 override 与贡献物的键。

**一条 recipe 不必整份选边——按格挑。** `qq-send` 就是混的：导航和判据走识别层（搜索框在树里
无名、两条结果行的名字都含联系人名而 a11y 表达不了「名字不含这一段」），只有"把焦点挪进消息
输入框"那一格走控件树（空输入框在识别层没有靶子，而它在树里叫会话名）。每一格挑最稳的那个，
比整份选一边稳。

判据不是猜的：`stream-desktop.exe see-probe <进程>`（mac：`stream-desktop see-probe <应用名>`，解锁状态下）打出来的元素表里如果一条 a11y 来源的都没有，
就走像素。agent 每次枚举都会打一行 `<进程> 的控件树枚举出 N 个可交互控件（Xms）`，看那个 N。

**判据是"有没有"，不是"快不快"。** 一次枚举现在是几十到几百毫秒（空树 ~50ms，Chrome 那种
几百个控件的真树 ~0.6s），没有"慢就是自绘"这回事。

**读到 0 之前，先排除四件不是"这个应用没有树"的事**：

| 看起来像"这个应用没有控件树" | 真相 | 怎么分辨 |
|---|---|---|
| **渲染端睡着** | 机器一闲下来（**不必锁屏**）Chromium 系应用把自己判成 occluded、挂起渲染端：树读回 0 或只剩几个无名 `Pane`，而**抬前台叫不醒** | 先 `wake`（`SendInput` 零位移，driver 的 `nudge`）再读一次 |
| 锁屏 | **锁屏不挡 UIA 读**，只挡投键鼠 | 同一时刻读一下 `chrome.exe`——那边有树就不是锁屏的锅 |
| 窗口不在前台 | 有的应用树是懒建的、激活才长出来 | 把窗口抬到前台再读一次；抬不动就是锁着（`SetForegroundWindow` 会回 false） |
| agent 回了空但没报错 | 查询本身建不起来时长得一模一样 | 看 agent 日志有没有 `查询建不起来` |

**"没读到"和"读到了否定答案"不许当成同一件事。** 这是这一面上最贵的一类错——两者长得一模
一样，而"没有"是更省事的那句。回执里的 `unbuilt` 就是为它准备的：字段在场 = 这个空不可采信。

**「只有几个无名 `Pane`」也是"没读到"，不是"读到了：没有"。** 这条特别点出来，是因为它**看起来
像个正经答案**——你拿到了窗口、拿到了节点、甚至拿到了类名，很容易读成"这个应用就是这么建的"。
实录（2026-09-07）：QQ 读回 8 个无名 `Pane`（含 `Intermediate D3D Window`，Chromium 的合成骨架），
据此写下过"QQ NT 根本不暴露 a11y 树"——**那条是错的**。叫醒之后它的树是齐的，消息输入框是个
`Edit`、name 就是会话名，`qq-send` 现在正靠它拿焦点。

**同一台机器上另一个应用有树，只能排除"agent 坏了"，排除不了"被测应用睡着了"。** 这是当时那次
对照实验唯一的漏洞：`chrome.exe` 238 个控件被当成了"所以 QQ 是真没有"，而 Chrome 那会儿正被人用着。

**确认了"真没有树"之后，把它写进 recipe：`"app": { ..., "a11y": false }`。** 这是**事实申报**，不是
优化开关：动作前的元素表读取从此不再枚举控件树（微信每步省 80–90ms），判据路 `readText` 不受影响，
`see-probe` 照样全量读（排错面永远要看得见 a11y 那一档在不在）。**判据是上面四件都排除之后**
`see-probe` 的 `elements` 里 `kind:"a11y"` 仍恒为空、且应用是已知自绘——QQ 那种"睡着了才空"的
**绝不能写**，写了就是把一次临时状态钉成永久结论（正是 agent 自己拒绝做的那件事）。写错的表现：
a11y 段永远缺席、`pinned` 固化永远不生效、点击全走坐标，每一步照样"成功"；唯一的痕迹是 agent 日志里
每次 `[see-read] elements … a11y=0ms(off)`。缺省 `true`，不写就是每步都问一次。

**`see` 的三种目标，按"它在不在表里"选，不按感觉选：**

| 写哪个 | 它问的是 | 什么时候用 |
|---|---|---|
| `text` | 屏幕上这段文字在哪 | 目标身上有字（绝大多数情况） |

**本地四档落空之后上不上模型，看这一步是不是 `optional`，不看目标类型。** 三种结局：

1. 认到了 → 直接做。
2. 认不到、**recipe 自己给了别的路**（这一步标了 `optional`：不在就换条路，比如"左栏看得见他就直接点，
   看不见走搜索"）→ 认不到**就是答案**，不上模型。它的常态恰恰是"不在这一屏"，拿模型去复核一个本地
   否定答案是白付一次远程调用——活体 2026-09-12 这一趟等了 31s，把整轮推过宿主 60s 超时。
3. 认不到、**也没有别的路**（必须找到的步骤）→ 才让模型兜底（OCR 漏认、字体太花）。

判据路（`expect` / `require` / `branch.when`）永远不上模型，与此无关。
| `icon` | 元素表里哪个是这个图标 | 没有字，但检测器会给框（工具栏图标那类） |
| `point` | **它在屏幕的哪个位置** | **前两个都指不到**：那东西在三张表里都不存在 |

**`point` 不是"更强的 text"，别拿它当万能档。** 三条硬边界：

- **有 `text` 能指的东西不要写 `point`。** 前四档本来就找得到，写了就是白付一次模型钱；
  而且第一次定位到的坐标还会被固化成句柄，把一个本来靠现读的稳定步骤钉在一个快照上。
- **`point` 只治"连框都没有"那一档**：大片空白的输入框——OCR 无字、检测器（训练来找图标和
  按钮的）不给框。QQ 的消息输入框正是这一类。写 `point` 之前先用 `see-probe` 确认它真的
  不在表里，别凭"我觉得指不到"。
- **判据位（`expect` / `require` / `branch.when`）写 `point` = 那条判据永远不成立。**
  判据不许调模型（这是引擎强制的），所以这一档在判据路上必然落空。判据只能用 `text` / `icon`。

**第一次之后它就不花钱了**：模型报出坐标后引擎会回读一次控件树，那个位置上若有带名字的控件，
名字就被固化下来，下一趟从梯子第一档走完。所以看到 `seeVia` 上写着 `pinned` 而不是 `point`，
说明固化生效了——**那两个不是同义词**，`pinned` 是拿固化的句柄查树，`a11y` 是拿 recipe 里
写的文字查树，分开记正是为了看得出这一趟走的哪条路。

**契约在 `docs/PACKAGE.md` §2**（`see` / `expect` / `blind` / `require` / `branch` / `interrupts` /
`input:"message"`），**看活界面与排查工具在 `drive-live-ui`**（`see-probe`、see 现场记录）。

**抢屏模式下人眼能跟得上它在干嘛**：坐标 `click` 的指针是**滑**过去的（约 250ms 缓入缓出、到位停
80ms 再按，20px 以内直接到位；`moveMouse` / `type` 不滑），屏幕顶上的接管指示条副句里带着当前步骤
（`wechat-send · 点候选里的他 (8/12) · 按 Ctrl+Alt+Esc 停止`——只有 recipe id 和步骤 `label`/`kind`，
**参数值绝不上屏**，`label` 里的 `{contact}` 也原样留着）。所以给动作步写 `label` 不只是为了日志：
它就是用户看到的那句话。条子仍只在真动键鼠时才亮，步骤文字不会把它点亮。不想要这句话：
`STREAM_DESKTOP_STATUS=0`（后端侧），runner 一条都不发。

下面是这个面独有的失败形状。


> **1–3 的共同点是全都表现成"跑完了，0 条"**，没有任何一步报错。**4 起是像素路独有的**——
> 它们的共同点换了一个：**每一步都"成功"，错却发生在别的地方**。

### 1 每轮开头没复位 —— 整条 recipe 在上一轮残留的界面上跑

- **症状**：`no items read`，而每一步都"成功"了。
- **真因**：**桌面应用是有状态的。** 浏览器每轮从 URL 进，天然回到已知状态；桌面应用长驻，
  上一轮的痕迹全留着。Telegram 跑完停在搜索模式，下一轮第一步「按名点进频道」匹配到的是
  **上一轮残留的搜索结果**（名字里同样带频道名），于是从第二步起全在错的界面上跑。
- **修法**：每轮开头加复位步骤，标 `optional: true`——首次运行时那个「取消搜索」按钮根本不存在，
  找不到正是正常情况。**`optional` 只给复位用**：把一个真该失败的步骤标成 optional，
  等于把 drift 变成静默错误。
- **复位要有守卫，别无条件打回初始态。** 状态是**读得出来的**："搜索框是不是空的"就是
  「placeholder『搜索』在不在」，"会话是不是他"就是「右侧标题是不是他」。正确的形状是先用
  `branch` 判状态、只在不干净时才复位（`qq-send-see` 就是这么写的）。无条件复位既多一次输入，
  也掩盖了"我们其实不知道现在在哪"这件事。像素路的复位手段是 `press: Escape`——步骤里只放行
  这一个键（回车用 `type` 的 `\n`）。

  > **这个「用 branch 手搓状态判断」正是状态图要收编的东西**，而桌面侧的识别层
  > （`DesktopPerception`，`src/replay/state-perception-desktop.ts`）已经建好：两档特征
  > （屏上有没有这串字 / 有没有一小块长成这样），一次 `identify` 只读一次屏，`on-failure` 触发。
  > **但它还没接线**——今天仍然只能手写 `branch`。要动这一块之前先读
  > `docs/ENGINE.md` §6（状态图）与 §7（视觉侧特征），别第三次手搓复位守卫。

### 2 读错了那一组列表（同一界面上有好几组同 role 的控件）

- **症状**：读到的条目和你想要的那批完全无关，或混着广告条/截断摘要。
- **真因**：Telegram 的搜索结果和主消息列表都是 `ListItem`，光靠 role 说不清读哪一组。
- **修法**：两道过滤各挡各的，别指望一道全包——① `observer.itemQuery` 吃 `{param}` 占位
  （`nameContains: "{q}"`），把当次搜索词编进查询；② `dedupeBy` 指向 `map` 抽出来的字段，
  抽不到的那些（截断的搜索摘要、频道里的广告条）自然出局。

### 3 源已被 drift 隔离，而你在对着一个根本没在跑的源反复改

- **判据**：返回是 `items: 0` + `errors: []`——与"跑成功了但没搜到"**一模一样**，从返回值上分不出来
  （`RepairLedger` 的既有语义，见 `adapters/replay/adapter.ts` 的 `shouldRun`）。
- **修法**：调 recipe 时**每改一版就 bump `version`**——换版本才解除隔离。

### 4 每一步都"成功"，错到两三步之后才以别的面目冒出来 —— 动作步没写 `expect`

- **症状**：失败报在一个和真因无关的步骤上。今天实录：「点会话行」没验证，点空了也照走，
  错在两步之后变成「正文没打进去」。
- **真因**：**动作没有后果检查。** 「我点了一个东西，接下来就该看见某个东西」——这条只要是可选的，
  就没人写：量过一次，桌面 recipe 的 21 个动作步里 **18 个没写**。
- **修法**：装载期强制二选一：给 `expect`，或给 `blind`（一句话说明为什么这一步没有可观测的
  后果）。`blind` 不是豁免，是把"忘了写"和"想过、确实没有"分开——有些转移在视觉方案里真的看不见
  （"输入框拿到了焦点"没有任何画面变化），那就写下来并说清责任转移到哪一步。
  **写不出经过验证的 expect 时别编一个**：没验过的 expect 比没有 expect 更坏，它看起来严谨、
  其实是猜的。

### 5 偶发点到"看着像目标、其实是另一个入口"的那一行

- **症状**：时好时坏。有时点开一个不相干的窗口，有时报"多命中、拒绝"。
- **真因**：**同一屏上有两处写着同一个名字**，而 OCR 的分段**每帧都可能不一样**。QQ 搜索联系人时，
  左栏同时有真正的会话行和最下面那行「进入全网搜索<名字>」；后者有时是一整段，有时被切成
  「进入全网搜索」+「<名字>」——切开时后半段就是一个和目标**全等**的假候选。
- **修法**：用 `see.not` 说出它和目标之间**语义上**的区别（`not: ["进入全网搜索"]`），排除是
  **按行**做的，所以怎么切都不影响结论。
  **别用位置去切**：按 x 把两者分开（真行 x=121、兜底行后半段 x=210）名字长一点就错位——
  那是把语义区别编码成像素阈值，会安静地失效。

  > **别和 `where` 搞混。** 有一个长得很像的东西叫 `where`（锚点 + 方向 + 距离），但它
  > **只长在状态特征上**，`See` 类型里没有这个字段——`see.not` / `see.below` 是定位层的收窄手段，
  > `where` 是识别层的。两边不通用，互相找不到。

### 5.5 `where`：识别层怎么钉「是不是**这个人**」

这一条不是给 `see` 用的，是给**状态特征**用的（`TextWhere`，`src/replay/desktop-recipe.ts`），
今天只在状态图那一侧生效。写在这儿是因为它防的是和上一条同一个错——**认错对象，下一格就是发错人**。

形状是照抄 UiPath 的 Anchor Base：`{ anchor: { text }, side: 'left'|'right'|'above'|'below', maxDist? }`。
四条判据：

- `maxDist` 的单位是**锚点框的宽（左右）或高（上下）的倍数**，不是像素——换分辨率不用重写。
- 锚点在**全屏**里找，不在收窄后的候选里找（锚点常常正好落在被排掉的那一条上）。
- **`where` 是过滤器不是选择器**：不做择优、不排序、不取最近，那是定位层的活。
- **一个状态如果全是带 `where` 的特征，那就是写歪了**：「我在哪个界面」该由不含位置的特征回答，
  `where` 只用来钉「我在跟哪个对象打交道」。

### 6 明明"多命中拒绝"了，它还是点了下去

- **真因**：识别层的梯子在 screen 段拒绝之后会落到**模板段**，而模板是上一轮种下的图，它会稳定地
  命中当初那一个。于是一次诚实的拒绝被后面一段变成一次沉默的点错。
- **现状**：已修——「一个都没认出来」照旧落模板（OCR 漏认是常事），「认出来好几个」当场返回空。
  这条留着是因为**同一形状会在别处重演**：任何"拿旧结果兜住新歧义"的兜底都有这个毛病。

### 7 三轮输一次、每次输在不同的一步 —— 应用的渲染端睡着了

- **症状**：同一条 recipe，有时全通，有时在**不同的**某一步 `expect` 不兑现。看起来像"焦点随机"。
  最迷惑的一档是：点击生效了（前几步的 expect 都过了），打进去的字却**在屏幕上哪儿都找不到**
  ——不在输入框、不在气泡、不在别的框里，凭空消失。
- **真因**：**Chromium/Electron 应用在机器闲置之后会把窗口判成 occluded、挂起渲染端**（锁屏只是
  触发方式之一，不锁也照睡）。挂起期间投进去的点击和按键**整份被丢弃**，而 `PostMessage` 照样
  返回成功、`PrintWindow` 照样出图——**三处都不喊**。所以它真正跟踪的变量是"最近有没有人碰过
  这台机器"，不是任何随机性。
- **一眼判据**：**控件树读回 0 个可交互控件 = 渲染端睡着 = 这一轮投什么都白投。** 本机实测
  （QQ，2026-09-08）：用户刚碰过 → 点击+打字 8/8、树里 `Edit` 2 个 / `Text` 60 个；闲置约 20 分钟
  → 0/6、树全 0；同一状态下先发一次**真实** `moveMouse` → 树回来、3/4。
- **修法**：动作之前先**叫醒**——发一次真实鼠标输入（`PostMessage` 不算：它不重置系统空闲计时器），
  然后**轮询控件树直到非空**，别睡一个魔法数（"醒没醒"是读得出来的）。抬到前台**叫不醒**，
  别把 `focus` 当叫醒手段。
- **代价要写清**：叫醒会移动用户的鼠标指针。用户正在拖文件或拖选文字时，指针跳走是会出事的。

### 8 `invoke target not found` —— 同一句话底下是两个不相干的病

- **症状**：a11y 路第一步就停，`invoke target not found: {"role":"Button","name":"消息"}`。
- **两个病，报错文本一模一样**：

  | 病 | 判法 |
  |---|---|
  | **渲染端睡着** → 整棵树 0 个控件 | agent 日志里那行 `<进程> 的控件树枚举出 N 个可交互控件`，N=0 就是它（见第 7 条） |
  | **名字对不上** → 树是活的，只是这个名字不存在 | 同一行报 N>0；再看 runner 打出来的"同 role 在场的有"那一串，答案通常直接写在里面 |

- **最常见的"名字对不上"是动态后缀**：QQ 导航按钮的可访问名是 **`消息 14条未读`**，而 recipe 写的是
  全等 `name: "消息"`——**未读数编进名字里了**，只有零未读那一刻才可能命中。这正是
  `A11yQuery.nameContains` 头注写死的那个坑（未读数、预览、时间戳每秒都在变），用 `nameContains`。
- **别只修第一步。** 拿到一份活的控件表就把**每一步**都对一遍：本机 2026-09-08 的 QQ，五个查询里
  三个指向今天树里**根本不存在**的东西（没有 `ComboBox`、一个 `ListItem` 都没有、搜索框无名），
  只有末尾两个（消息输入框 `Edit`、`发送 Button`）还在。**那不是"旧了、有点飘"，是它描述的那个
  界面已经不存在了**——一步步修会一次次重新发现同一件事。
- **通用教训**：**一句错误文本底下坐着几个病，就等于没有判据。** 修法不是让文本更长，是给每个病
  找一个**各自独立可读的**判据（这里是"树里有几个控件"），然后在文档里把两者并排放好。

### 9 排查像素路，别对着事后截图猜

- **教训**：事后截图 + 步骤日志推不出"它当时看到了什么"。今天据此编过一个「兜底行先渲染、真结果
  晚一步」的解释，而用户盯着屏幕看到的是两行同时出现——**猜出来的因果读起来和量出来的一模一样**。
- **工具**：后端环境变量 `STREAM_DESKTOP_SEE_TRACE=1`，每次 `see` 决定落一条 JSON + 一张叠图到
  `<dataDir>/desktop-see/<sourceId>/trace/`：候选全集、全等/包含的分组、选中的那个、没选中的原因，
  叠图上候选描黄边编号、选中的描红。用法见 `drive-live-ui`。
- **先排除"眼睛根本没睁开"**：每个 `see` / `expect` 都以 `ocr-missing:` 或 `ort-missing:` 失败，
  是平台包 `bin/` 里缺了读屏模型三件或 ONNX Runtime 动态库（两平台同一判据，**不回落**到任何
  别的 OCR），和 recipe 无关——去补文件（`capabilities/desktop/README.md` 的出货清单），别改 recipe。
  `see-probe` 回执的 `engine{name,version,threads,lib}` 就是"跑的是哪一份引擎"的证据。

### 10 点一个弹层里的东西，点了个空 —— 弹层是「随主窗活着」的，抬它前台它就关

- **症状**：搜索候选弹层（微信：`Weixin.exe` 另一个顶层窗口，标题「Weixin」，`cdp_pages desktop`
  里 `foreground:false`）明明在屏幕上、OCR 也找到了候选，点下去会话没切、下一步 `require` 判
  「不是他」abort。消息模式（`input:'message'`）点得中，但消息模式打字**触发不出**这个弹层。
- **真因**：`window` 步把范围换到弹层之后，抢屏默认抬**被 scope 的那个窗口**——就是弹层本身。
  主窗一失焦，这类 owned popup 立刻自己关，点击落在它消失之后的空位上。
- **修法**：那一步 `window` 加 `ownedPopup: true`——范围切到弹层找候选，前台仍钉在主窗
  （`recipe.app`）。弹层是 owned window、画在属主之上，主窗在前台时坐标点击落在它的像素上照样中。
- **别乱置真**：独立模态对话框（文件选择框那种、自己该拿焦点的）不是这一类，它就是要 `focus`
  抬它自己。判据：主窗失焦它会不会消失。

### 11 系统文件对话框别手抄四步——用 `pickFile`

- **形状**：前一步把对话框弹出来（点「发送文件」图标 / 「加载未打包」），下一步 `{ kind:'pickFile', path:'{path}' }`
  自己等它出现、写文件名框、让它拿焦点回车、等它消失、范围换回。契约见 `docs/PACKAGE.md` §2.4 那张表。
- **为什么不写 `invoke` 点「打开(O)」**：确认键**不一定在树里**——微信「选择文件」对话框同一台机器两次抓树
  一有一无（2026-09-18）；文件名框拿焦点 + 回车才是活体验过的路。树里有确认键 `pickFile` 只当备选。
- **判据别写完整文件名**：微信把长文件名截成「中基协登记备...2期.pdf」，全名恒不命中。`format:'path'` 参数
  派生了 `{path_stem6}`（主干前 6 个字）/ `{path_ext}` / `{path_kind}`，判据用片段做包含匹配。
- **图片没有文字判据**（微信只画缩略图），按 `{path_kind}` 分流：图片那一路 `pickFile` 写 `blind`，
  前面的参数 `branch` 带 `unverified:'image-no-caption'`，回执上"没验"和"验过"分得开。
  **输入框为空时图片在选中那一刻就发出去了**，`send:false` 挡不住——这是微信的行为，不是 recipe 能改的。
- 失败前缀 `pickFile/dialog-missing` / `edit-missing` / `set-value-failed` / `dialog-still-open` 各指一段，
  回执 `pickFile[label].ms` 分段计时——"这一步慢"先看是哪一段。
