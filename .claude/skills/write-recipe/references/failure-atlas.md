# 故障查表（Failure Atlas）

给 code agent 查的。**分类轴 = 数据/控制流经过的六道边界。** 任何一次故障都坐落在某一道边界上；
先定边界，再查条目。每条给：**症状 / 一眼判据 / 真因 / 修法**。

> 加新条目时：先问"它坏在哪道边界"。答不出来，说明问题还没定准，别急着写条目。
> 站点特化的经验放最后的**附录**，按 facility 分节，不要混进通用层。

六道边界：

| # | 边界 | 问的是 |
|---|---|---|
| 1 | **会话** | 这个 tab 是不是我的？还是不是刚才那个页面？ |
| 2 | **时序** | 我在该看的时候看着吗？ |
| 3 | **观察** | 我读到的，是不是页面上真实存在的全部？ |
| 4 | **操作** | 我的动作真的作用到页面上了吗？ |
| 5 | **映射** | 读到的东西，变成 item 了吗？ |
| 6 | **宿主** | 进程/容器本身活着吗？ |

---

## 边界 1 — 会话

### 1.1 操作"随机不生效"／feed 莫名其妙换了一批
- **判据**：`locate` 探针 `vp=N known=0`（视口有卡，一张都不认识）；或账本 `ledger=0`。
- **真因**：**有第二个东西在动同一个 facility 的 tab。** 最常见是一条按 cadence 跑的定时流，
  周期性 harvest 同一站点，把浏览 feed 冲掉、账本作废。
- **修法**：退役掉抢 tab 的定时流（把 pull 型浏览会话和 push 型定时入库彻底分开）；前端单飞；
  调试期不要另开这个站的第二个会话——采集骑的是**用户自己**那个登录，抢的是他本人。
- **通用教训**：**"我的操作没生效"，先查资源是不是被别人抢了，再改自己的代码。**

### 1.2 续抓（loadMore）拿不到东西 / 滚个没完
- **判据**：`rideCurrentPage` 那次运行 `targetCount` 填的是累计值。
- **真因**：续抓那一轮的 network observer 从零开始，**只看得见这次新触发的 XHR**。
- **修法**：`targetCount` 传**增量**。

### 1.3 tab 空闲被回收后账本还在用
- **判据**：idle 很久之后第一次操作失败。
- **修法**：idle TTL 到了就 `reset()`（丢账本 + 关 tab），别拿废账本去定位。

### 1.4 注入了 cookie，页面却全程是游客（而且不报错）

> **先确认你真的在注入 cookie。** 采集浏览器**不再注入任何 cookie**——它是用户自己的 Chrome，
> 登录态本来就在里面（`src/replay/transport.ts` 的注释就写着这件事）。这条只剩两个现场：
> **作者流程**用 `COOKIE_HEADER`/`COOKIE_DOMAIN` 抓一个"你没登录的会话"，以及 **HTTP 档**
> （`kind:'http'`，服务端裸 fetch，broker cookie 由 `cookieDomain` 门控）。采集不出数**别往这查**。

- **判据**：页面里 `document.cookie` **没有登录 cookie**（站点自己种的那几个倒是在）；
  站点接口回"未登录"（夸克 `401 code 31001 require login [guest]`）。
  ⚠️ **`ctx.cookies(url)` 会说"可见"——别信它**（见下"通用教训"）。
- **真因**：注入的 cookie domain **没带前导点** = host-only，Chromium 只发给 apex，
  **不发给站点真正运行的子域**（`pan.quark.cn` / `www.*`）。
- **修法**：`parseCookieHeader`（`src/replay/cookies.ts`）已在源头统一补点（幂等），
  作者侧的 `injectCookies`（`src/replay/browser.ts`）走的就是它——别绕开它自己拼 cookie 对象。
  详见 `login-and-session.md` §2.1。
- **通用教训**：**Playwright 的 `context.cookies(url)` 不模拟 host-only 作用域**，把 host-only cookie
  报告成"对子域可见"——一个假读数骗掉整轮诊断，还会把人引向"这站会话短命、得改扫码"的错误结论。
  **判登录态只信两样:页面里的 `document.cookie`，或一次真实请求的返回**（渲染也会骗人：SPA 带着有效
  cookie 也可能被弹回落地页）。**有反例在（同样 cookie 在别处能用），就别归因于"凭据不行"，先怀疑自己的注入。**

## 边界 2 — 时序

### 2.1 偶发抓空 / 连续两次刷新第二次空
- **判据**：采集曲线显示只有"某次滚动碰巧触发的请求"有数据；换个时机就空。
- **真因**：**`network` observer 在 `goto` 之后才挂上。** 页面加载时发出的首批请求，观察者还没 start，
  就永远不存在。
- **修法**：先 `observers.start()`，再 `driver.goto()`；带 network observer 的 recipe **强制走一次加载**
  （观察者得*看着*这次加载发生）。
- **通用教训**：**任何监听/订阅/拦截，先确认它在被观察的事件之前就位。"偶发"往往是时序，不是随机。**

### 2.2 移动之后立刻读，读到旧内容
- **判据**：滚动后视口 id 和上次一模一样 → 被误判成"没滚动"。
- **真因**：feed 异步重渲染。
- **修法**：每次移动后 **dwell**；**空视口不是终态**，容忍连续几次空读。

## 边界 3 — 观察

### 3.1 抓到的和页面上看到的对不上 / 少了一整批
- **判据**：**采集曲线第一次滚动前是 `0`**（`items 0,20,…`）；且 `locate` 探针里目标卡的 `docY` 大得离谱。
- **真因**：**首屏那批内容是 SSR 进 `window.__INITIAL_STATE__` 的，根本不发 XHR。**
  只挂 `network` observer = 静悄悄丢掉第一批，且**不报错**。
- **修法**：补一个 `trigger:'entry'` 的 `state` observer 读那个全局，和 network 那批合并。
  注意两者**字段命名不同**（见 5.1），要用 per-observer 的 `input.mapping` 各自归一化。
- **通用教训**：**首屏数据未必来自 XHR。**"没有请求"和"请求没抓到"是两回事，前者用 network observer
  永远等不到。

### 3.1.5 `network` observer 恒 0 条，reason 里带 `network body read failed: -32000`

- **判据**：失败 reason 形如
  `recipe produced no items (at <url>; network body read failed: {"code":-32000,"message":"No data found for resource with given identifier"})`。
  关键是**恒定**——同一 recipe 连续两轮同样挂，而同一档上别的 recipe（body 小的）一直正常出数。
- **真因**：body 读早了。CDP 里 `Network.responseReceived` 只表示**响应头**到了，主体可能还在传；
  `getResponseBody` 此刻拿到的就是这条 -32000（注意它是 "No **data** found"，不是
  "No **resource** found"——DevTools 认得这个 requestId，只是缓冲里还没有内容）。
  body 完整可读的信号是 `Network.loadingFinished`。
- **⚠️ 别归因成"缓冲区把 body 逐出了"**：同一条错误消息的两个成因方向完全相反（读早 vs 读晚），
  照逐出去查会去调 `Network.enable` 的 `maxResourceBufferSize`，白费一轮。**分辨判据**：读早了 =
  跟 body 大小强相关、换个站就 100% 复现（活体 2026-07-28，douyin 搜索结果 JSON 大几百 KB，
  两轮全灭；同期 xhs feed 从没失手）；逐出 = 随机抖动、和大小无强相关。
- **守在哪**（`observer-pipeline.ts`）——`responseReceived` 只登记 url→observer 的匹配，
  读 body 推迟到 `loadingFinished`；`loadingFailed` 撤销登记；始终没等到完成信号的，在 `flush()`
  收尾时兜底读一次（诊断写成 `network body unread (response never finished loading)`）。
- **顺带的判读纪律**：一条 body 读失败**只损失这一条**，其余照收。所以"读失败"和"整轮 0 条"之间
  并没有错误传播——只是有些 recipe（如 douyin-search）每轮只发一条命中的 XHR，那一条挂掉恰好
  等于全灭。**别把"条数少"误诊成"一个失败清空了整批"去改错误处理。**

### 3.2 读 `window` 上的 store 拿到 `{}`
- **真因**：V8 `returnByValue` 对 Vue/MobX 的 reactive Proxy 序列化出空对象。
- **修法**：在**页面里** `JSON.stringify` 之后再跨边界（`readStateExpr` 就是干这个的）。

### 3.3 `readyWhen` 明明为真，却读到半成品
- **判据**：**先量，别猜**——10ms 级采样打出这个状态条目的填充时间线（怎么量见 `observing.md` §5.5），
  看采样里是否真的出现过「`readyWhen` 已真、内容字段还空」的那一帧。没量到这一帧就不是这条故障。
- **真因**：这个字段不是"就绪"信号，它从条目存在的那一刻起就为真，无法当门。
- **⚠️ xhs 的 `comments.firstRequestFinish` 不是这种字段**，别把它当已知案例照抄：2026-07-27 实测它是
  **最后**翻的信号（视频笔记 355ms 才真，晚于内容填完的 148ms），是有效的、也是最严格的 gate。它曾被
  想当然地判成"条目一出现就真"，据此在 `locate` 之后挂了一个 500ms 固定盲等——理由错、注释还写得头头是道。
- **修法**：换一个真正的就绪判据；或把 `pollMs` 调小，让 offer 贴合真实就绪时刻而不是 poll 边界。
  **别加固定 dwell**：它把 observer 的 poll-until-`readyWhen` 架空——快的时候白等，慢的时候照样读到半成品。

### 3.5 一次搜索里**几个源同时**报 `member "…" timed out after 25000ms`
- **判据**：**"同时"就是线索**。几个互不相干的源不会一起坏，但同一件事可以发生几次。
- **真因（其一）**：lane 映射只在进程内存里，**后端一重启，上一批 tab 全成孤儿记录**。复用前的
  探活走 `transport.url()`，而它吃的是中继默认超时 **30s** —— 比每个成员 25s 的预算还长，于是
  探活自己把预算烧光了，报出来却是"这个源超时"。**下一次搜索就正常**（第一次已经把死记录清掉），
  所以它长期看起来像"偶发"。**守在哪**：探活自带 2s 死线（活着的标签实测 10ms 就答）。
- **真因（其二）**：重登面板开着时，登录流程占着那条 lane（占到用户扫完，分钟级），采集排队排到
  超时。**守在哪**：租借带 `purpose`，采集撞上 `login` 当场抛 `LaneBusyForLoginError`，并被
  `blockedOf` 映射成"需要登录"——画按钮，不是红字。
- **通用教训**：**任何"等外部答话"的探测都必须自带死线**，而且那个死线要**短于调用方的预算**。
  继承一个更长的默认超时 = 把别人的预算烧光还嫁祸给他。

### 3.6 采集标签停在空白页，永不跳转
- **症状**：搜索开了 tab，停在 `about:blank` 一动不动；成员随后超时。
- **真因**：新建 lane **故意**落 `about:blank`（这样一次搜索只加载一次页面，而不是"建标签载一遍、
  observer 挂好再载一遍"），但扩展的 `waitForNav` 判据是「已经离开 about:blank 且文档就绪」——
  目标本身就是空白页时这条永远不成立，`newTab` 命令空转满 30 秒不返回，**后端那句 `goto` 根本
  轮不上**。2026-07-29 已修（`url === 'about:blank'` 直接返回）。
- **教训**：把某个"中间态哨兵值"（这里是 about:blank）改成**合法落点**时，先搜一遍谁把它当哨兵用。

### 3.4 一次运行**永不返回**（不是失败，是挂着），整条 lane 被占死
- **判据**：日志停在某个 step（活体那次是 `step#0 open fallback-nav 549ms`），**之后没有 `state-wait`、
  没有 `TOTAL`、没有失败截图落盘**；curl 90s 超时拿到 `http=000`，而服务端那次运行**几分钟后仍未结束**。
  后续同 facility 的活全部排在它后面等不到——xhs 是单 tab 独占的。
- **真因**：**渲染进程崩掉/半死之后（上一轮 `page.goto: Page crashed`），下一次的 `readState` 永不返回。**
  Playwright 的 `page.evaluate` **不吃 timeout 参数**，页面不答话它就那么等着。observer 的 `maxWaitMs`
  是**两次读之间**才检查的，一次读挂住就走不到下一轮——总上限形同虚设。`policy.maxTaskMs` 同理：
  它只在 step 的进出口检查，卡在 step **内部**的读走不到任何检查点。
- **修法**：单次读已经有上限了（`observer-pipeline.ts` 的 `stateReadTimeoutMs`：`maxWaitMs/3`，
  夹在 1s 地板和 5s 天花板之间）。超时只结束**这一次读**、继续 poll，`maxWaitMs` 才真正成为总上限。
  诊断里会出现 `read timed out Nx (>…ms each) — the page stopped answering`，**别把它读成"state 不存在"**。
- **⚠️ 这是止血，不是根因**：根因是渲染进程会崩（页面从此不答话；实测出处是 detail recipe 恒 502），这一层不修它。
  这一层只保证"崩了之后失败是**有界**的"——lane 会还回来。
- **通用教训**：**一个总预算只在循环边界被检查，就只在"每一步都会返回"的前提下成立。**
  无界的挂死比一个明确的 502 更坏：502 至少会释放资源。

### 3.7 「没读到」被当成了「读到了：没有」——这道边界上最贵的一类错

- **症状**：一个"没有 / 没找到 / 是 0"的判定，后面所有推理都建立在它上面，而它本身是假的。
  它不报错，而且**是更省事的那句**，所以天然会被接受。
- **判据**：拿到 0 / null / 空数组时，问一句「**我确实读到了吗**」。答不出"是"，这一格就不是
  一个答案，是一次失败的观测。
- **修法**：**两者必须走不同的分支。** 读不到就报"没验到"，不许报"验过了、结果是没有"。
  接口上就要分得开——布尔字段答不了这个问题，得让"没验到"有自己的取值（`see` 回执里的
  `unbuilt` 就是这么用的：字段在场 = 这个空不可采信）。
- **四副面孔**（同一晚上撞到的，形状完全一样，2026-09-08）：

  | 长什么样 | 实际是 |
  |---|---|
  | 控件树读回 0 个可交互控件 | 应用的渲染端**睡着了**（机器闲置），不是"这个应用没有控件树" |
  | `grep -c <串> <exe>` 回 0、退出码 1 | `grep` 带 `-I` **默默跳过二进制文件**（加 `-a` 之后是 1） |
  | 守候判"解锁了没"：`tail -1 \| grep -v LockApp` | 探针输出从一行改成两行，新那行天然不含判据字段 → **恒判成解锁** |
  | 「字打进搜索框了吗」两格判据同时为真 | 第二格命中的是别处一段同名文字，**恒真 = 没有判据** |

- **通用教训**：**判据依赖的输入格式，如果是你自己也会改的东西，它迟早会静默反转**，而反转
  后的答案往往正是你希望看到的那个。所以判据要**先要求看见肯定的证据**（"读到了 `fg=` 这一格"），
  再谈它的取值——而不是直接对一个可能根本没读到的东西取反。
- **同形的三处**（这条不是孤例，是本仓库反复出现的形状）：`empty_may_be_unbuilt` 那面旗、
  `a11y_hopeless` 那种黑名单（它最狠：把**一次**读不到硬化成**永久**事实）、
  以及 `expect` 把"多命中"和"没命中"一起判失败——那一下把一条**已经发出去的**消息报成了失败，
  而调用方看到失败会重发。

## 边界 4 — 操作

### 4.1 定位不到卡片 / 一直 fallback-nav
- **判据**：probe `step#0 open fallback-nav`。**注意它能出数据、不报错**——指标是绿的。
- **真因**（按频率）：账本/DOM 对不齐（→ 边界 1、3）；点击目标选中了**隐藏的零尺寸 anchor**；
  移动后没 dwell（→ 2.2）；**落脚点根本不是 feed**（见下条）。
- **每次都 fallback、而且 `locate: MISS idx=-1 after 0 jump(s) + 0 wheel(s)`**（0 次移动 = 视口里
  一张卡都没读到）→ 跑完打 `/api/facilities/<f>/page` 看 tab 停在哪。停在 `about:blank` 或目标详情页
  = 落脚点错了，不是定位算法的问题：`restore: back` 回到的是冷启空白页，下一次还从空白页开始，
  循环自我延续（→ `pipeline.md` §4.1）。先查 recipe 的 `entryUrl` 是不是被填成了 `fallbackUrl`。
- **用 `locate` 段的耗时一眼分流**（xhs-detail 实测）：**5–23ms = 健康**（卡就在 DOM 里，读坐标一步过去）；
  **1000ms+ = 它在空转**（找一张根本不在页上的卡，攒满 `blankReads` 才放弃）。**中间值几乎不出现**——
  所以这个数是二元判据，不是性能指标。看到四位数就直接去查落脚点，别去调定位算法。
- **修法**：定位优先**直接读 DOM 里目标 anchor 的 `boundingRect`**，别外推（见 `pipeline.md` §3）；
  点击**只认看得见的候选**——一张卡常带好几个同 id 的 anchor，DOM 序第一个可能是零尺寸的。
  **驱动这边没有"可操作性检查"这层保险**：它按 rect 算中心点直接发 CDP Input，而零尺寸元素的
  中心是 **(0,0)**，于是**点在页面左上角**（那儿常常正是站点 logo），笔记没打开、`observeOpened`
  白等再退 fallback。**注意这类失败不会报"元素不可点"，它会报"打开了但不是那一页"**（或干脆什么
  都没发生），所以别指望驱动替你挡住。判据见 `card-id.ts` 的 `VISIBLE_EL_FN_SOURCE`。
- **通用教训**：**能出数据的降级路径是最阴险的故障**，所有降级分支必须打点。

### 4.1.5 每一步都"通过"，但结果是错的；失败在几步之外以无关症状露面
- **判据**：probe 里各步 `expect ok` 一路绿到底，而**最终产物是空的或是错的**。回头看那个 expect
  的选择器——**它在动作之前就已经成立吗？** 是 = 这一步从来没有被监督过。
- **真因**：`expect` 恒真。判据只问"动作之后它在不在"，不问"动作之前它在不在"；一个动作前就成立的
  判据永远不会失败，看起来像监督、实际是装饰。于是动作没生效也照样往下走，后面的步骤在**错误的
  前提**上继续操作，最终以一个离真因好几步远的症状失败。
- **活体**（2026-07-30 `zhipu-create-key`）：建 key 那步判据写成「表格最后一行有复制图标」，而列表里
  本来就有一把旧 key、那图标一直都在 → 「确定」没建成也判过 → 下一步点了**旧那行**的复制按钮 →
  最后报「抽取命中 0 处」。四步全绿，报错指向抽取，真因在两步之前的一个假判据。
- **修法**：判据必须**动作前为假、动作后为真**。"多了一行/多了一个"用 `expect.countIncreases`，
  别用 `present`（那个选择器本来就命中着旧的那些，必然恒真）。写法见 `authoring.md` §3.5。
- **守在哪**（`actions.ts`）：动作**之前**先读一次判据，已经成立就抛 `StepExpectVacuousError`，
  并且**不执行动作**——判据都不成立，就别再去改页面状态。豁免要显式写 `alreadyThere: true`。
- **通用教训**：**手动驱动页面时你每一步都在监督（数命中数、看可见性、点完读一眼）——
  写成 recipe 时监督必须跟着一起固化。** 只固化动作、不固化判据，等于把一段看得见的流程变成瞎跑。
  这和 4.1 的"能出数据的降级路径最阴险"是同一条：**绿灯不等于对**。

### 4.2 遍历元素时报 stale / 索引错位

- **修法**：**别按索引逐个遍历**，用一条精确的选择器一次锁定目标。

### 4.3.5 隐藏 tab 上一次点击要几十秒（不是几百毫秒）
- **症状**：`humanize` 那一步的耗时忽快忽慢，从 0.4s 到 8s 都有；极端情况一次可信点击 **40 秒**。
- **判据**：读一次 `document.visibilityState`。是 `hidden` 且**没开 focus 仿真**，就是它。
- **真因**：隐藏 tab 的可信输入在**等下一帧**，而浏览器不打算给看不见的 tab 画 —— 每个输入事件约
  等 4 秒，一次点击 10 个事件。**页面自己在忙（不停加载图片）反而会顺带产帧**，所以在真实站点上
  它表现为"忽快忽慢"，在静态页上才露出稳定的 40 秒（2026-07-29 用 example.com 量出来的）。
- **修法**：确认 lane 建好时发过 `Emulation.setFocusEmulationEnabled`（`browser-ext.ts` 的 launch）。
  **别去想着"替它产一帧"**：那条路走过，逼一帧只让流水线热一小会儿、凉了就打回原形
  （实测 267ms / 1.2s / 39.8s，忽快忽慢），今天 driver 里已经一帧都不逼。
  完整四档对照见 `session-runtime.md` 的 `visibility` 一节。
- **开了仿真还是慢（秒级），去看回执那一半**：2026-09-03 实测，仿真开着的后台标签一次点击仍要
  5.9–9.7 秒，而**事件本身 262ms 内就全都送到页面了**——慢的是每个鼠标事件的 ack（0.5–0.9s×11）。
  今天扩展对可信鼠标事件**发了就算、不等回执**（`driver.ts` 的 `FIRE_AND_FORGET`），实测
  0.19–0.33s。所以再遇到秒级点击，先确认用户装的扩展是不是旧版本——**旧扩展 + 新后端**那一档
  会原样退回 5–10 秒，而且没有任何一处会喊。

### 4.3.55 一个 `settle` 步骤稳定地卡满 15 秒（判据永远不会成立）

**先查这一条，再去查下面 4.3.6。** 两者症状一样（这一步慢得离谱），真因完全不同，
而**帧数一眼就能分开**：

```
[recipe-probe] <source>  step#1 settle timeout 15056ms/52帧 ← 没等到判据，照常放行
```

- **52 帧 = 截图一直在产**，只是内容一次都没满足判据 → 是**判据写错了**，看这一条。
- **帧数个位数、每帧本身就要几秒** → 是**没帧可截**（窗口没显示在屏幕上），看 4.3.6。

- **症状**：耗时**稳定**贴着 `SETTLE_DEFAULT_MS`（15000ms），换台机器、换时段都一样。
  而 4.3.6 那种是忽快忽慢（0.11s ↔ 30s）。
- **真因**：settle 的判据是「**变过了** + 停住了」，而"变过了"是相对**开始等的那一刻**取的
  基线。如果那次变化是**上一步**触发的（点一下按钮让它重新加载一张图），而上一步自己比那次
  重绘还慢，等这一步开始看时画面**早就是终态**——基线就是终态，此后永不改变，于是必然等满
  timeout。**它不致命**（timeout 照常放行），所以整件事唯一的症状就是"这一步很慢"。
- **修法**：给这个 settle 开 `alreadyStable: true`（只要求连着 N 帧不变，不要求相对基线变过）。
  **开之前先确认上一步的耗时可靠地长于那次重绘**——否则"连着 N 帧不变"会在**旧画面**上立刻
  满足，你拿到的是上一张图。
- **活体（2026-09-03，东财登录）**：`step#1 call` 连续三次 15.0–17.7s，而识别本身 10ms、
  ddddocr 容器还醒着。开了 `alreadyStable` 之后：**399ms / 639ms**。

### 4.3.6 一个 `scroll` / `settle` 步骤慢得离谱，或报 `Page.captureScreenshot ... 没有产出帧`
- **症状**：probe 里某一步几秒到几十秒，而这一步该做的事只要几百毫秒；或者 outcome 直接带上面
  那句 reason（截图命令在扩展侧有 1.5 秒上界 `SCREENSHOT_BUDGET_MS`，到点回一个明确失败）。
- **判据**：看这一步**要不要真帧**。今天采集路径上只剩 `settle`（逐帧截图比字节）落到
  `Page.captureScreenshot`——**driver 本身一帧都不逼**，所以 `scroll` / `goto` / dwell 都不再是
  嫌疑人。一张整帧 JPEG 正常是 286–392ms；慢到秒级就是没帧可截。
- **真因在 OS 那一层，不在页面、不在中继**：`Page.captureScreenshot` 要合成器**真的产出一帧**，
  而 Chrome 窗口没有真的显示在屏幕上时它不产帧——**被别的窗口盖住、最小化、锁屏都算**。
  实测挂住的时长 12.0s / 18.5s / 26.1s / 30.0s（30.0s 是后端中继的闸门兜底，不是命令自己回来了）。
  **这也正是"用户手点秒开、我们几十秒"的差别所在**：他点的时候那扇窗就在他眼前亮着。
- **`Emulation.setFocusEmulationEnabled` 救不了这一格，别去查那条腿。** 它给的是"页面被当成
  有焦点"这个谎，可信输入等的正是这个谎（4.3.5 那一格靠它，39.8s → 165ms）；帧不归页面管。
  A/B 对照：开关 ON 也照样挂（18.66s、12.03s），开关 OFF 挂（26.08s、30.00s×4），快的时候两边
  都是 0.11–0.21s —— 两个 arm 都挂过，**开关不是自变量**。
- **导航步（`entry` / `step#0 goto`）偶发挂满 ~30 秒是另一回事，别往这条上归因**：`goto` 不逼帧，
  所以它挂住与截图无关。它的归因走下面 §4.3.61 那张分跳表。
- 要看底层到底卡了多久，去 `GET /api/debug/log?channel=ext-cdp` 看四条记录：扩展侧
  `slow-command` / `slow-command-done`，后端侧 `relay-slow` / `relay-timeout`。读法见 §4.3.61。
  **那个环只留 200 条且重启即清空**，所以事后翻旧账要读落盘那份：
  `grep '"ext-cdp"' data/debug-failures.jsonl | tail`（只收 `ok:false`，这四条正好都是）。

### 4.3.61 一条 CDP 命令挂了几十秒 —— 读分跳表定位是哪一跳

- **症状**：某条命令（实测最常见是 `Page.navigate`）挂满将近 30 秒。30s 是后端中继的闸门
  （`shared/browser-relay/relay.ts`），不是命令自己回来了。**这道闸门是真的会被撞到的**：
  `Runtime.evaluate` 实测过 `30414ms`（中继侧总共等了 `30553ms`）与 `64096ms`，另有一条等满
  `30000ms` 干脆没有回执的记录（`data/debug-failures.jsonl`，08-29→09-05 共 509 条 `ext-cdp` 样本）。
- **先排掉已经实测排掉的**（别重摸）：不是网络（同时段宿主 `curl` 2.1s）、不是"后台标签导航
  天生慢"（实测 1.09s）、不是被挂住的截图堵住了同一个 tab（实测 1.12s）、不是 MV3 SW 被回收
  （冷启探针 0.32–0.39s ×3）、不是 `readyState` 在等帧（饿死的标签上 0.49s 就 complete）。
- **判据**：一条命令要走五段（后端发出 → SW 收到 → SW 发 CDP → tab 回话 → 后端收到）。
  两侧各记各的账，同一条命令靠 `command` + 时间邻近对齐。按顺序问三句：

  | 问 | 看哪个字段 | 是它 → 慢在 |
  |---|---|---|
  | `wireMs` 是不是大头？ | 后端 `relay-slow` | WS 那两段（去程+回程，不区分） |
  | `cdpIssued:false`，或 `preCdpMs` 是大头？ | 扩展 `slow-command` | SW 到 tab 之间的 `ensureAttached` / 域校验 |
  | `cdpMs` 是不是大头？ | 扩展 `slow-command-done` | tab / Chrome 内部，命令自己没回执 |

  **实测那条 `30553ms` 就是这样归因的**：WS 那两段（去程+回程）合计只有 `139ms`——排队和派发都不慢，
  慢的是 CDP 命令自己那一跳（tab / Chrome 内部），relay 和 SW 都被排除。
- **按命令名分档没有意义**：同一批 509 条样本里 `Page.navigate` 出现 9 次，耗时 `3450–7379ms`，
  但 `preCdpMs` 全部是 `0–1ms`——真正共同的是"个位数的 `preCdpMs`"，读它就能排除 relay/SW，
  和命令叫什么无关。另有一批更长的 recipe 级失败（不是单条 CDP 命令，是整个 step）：最慢
  `step#0`/`step#2` 的 `click` 耗时 `34680–44847ms`，整条 recipe `71.0s–139.2s`。
- **后端有 `relay-timeout`、扩展侧一条 `slow-command` 都没有** = 命令根本没送到 SW
  （SW 被回收 / WS 半开）。两条都有 = 送到了、SW 手里挂着。
- **`swMs` / `wireMs` 报 `unknown`** = 用户装的扩展是不带这个字段的老版本，让他重新加载扩展再撞一次。
  **别把 unknown 读成 0** —— 0 会把整段时间栽给 SW。
- **`wireMs` 可以是小负数**（两侧时钟分辨率 + 序列化开销），那是噪声不是异常；只有量级到秒才有意义。
- **别拿两侧的时间戳做减法。** 后端跑在 WSL（墙钟偶发回退、单调钟偏快约 7.6%）、SW 跑在 Chrome 里，
  是两个钟。所有报出来的时长都是**同侧两点之差**，`wireMs` 是**两个同侧时长相减**得到的
  ——这也是它分不出去程/回程的原因。设计与理由：
  `internal design record`。
- **修法**：这一格目前**只有观测没有修法**——归因已经明确指向 CDP 命令自己那一跳（tab / Chrome 内部），
  但那一跳内部还没有更细的分档。撞到一次就照上表归因，再谈修哪一跳。**别去调大超时**，那只是把等待写长。
- 注意 `settle` **守不住自己的 timeout**：deadline 只在两次截图之间检查，一次截图挂满上界就穿了。
- **修法**：先问这一步**是不是真需要一帧**。"等 DOM 稳定"「等列表不再变长」都不需要——把它换成一个
  Tier-A 的 `evaluate` 步骤在页内轮询（几十毫秒），别为它去截十几张图。真需要真帧时，前提是那扇
  Chrome 窗口此刻在屏幕上看得见。**别反过来调大 timeout**：那只是把等待写长。
  （2026-08-12，google-search，同一条 recipe：挂 `settle:{timeout:1500}` 跑 **38.5s**、
  只留 `scroll` 跑 **30.3s**、两者都去掉 **2–3s**。）

### 4.3.65 `outcome=ok`，条数却总是差一整批（新写的 scroll + dwell recipe 尤其要防）

- **症状**：一条 scroll 型 recipe 稳定只拿到 `targetCount` 的一部分，**不报错、不留失败现场**，
  只是少。多跑几次还是少。
- **真因（其中一种，最难看出来）**：**有的站点的"下一批"要合成器真产出一帧才触发。** 而
  **采集 driver 一帧都不逼**（见 `session-runtime.md`「为什么今天一帧都不逼」），后台标签在
  dwell 期间产不产帧由 OS 那层"这扇 Chrome 窗口显不显示"说了算——被别的窗口盖住 / 最小化 /
  锁屏都算。窗口不显示 → 下一批不来 → `noProgressStop` 提前收手，而**每一步都"成功"了**。
- **判据**：把 Chrome 窗口拿到前台，同一条 recipe 再跑几轮对比条数。前台够数、后台不够，就是这一格。
  （辅助判据：打几发 `GET /api/facilities/<name>/page/screenshot`，**500 + 约 1.5s** = 此刻没帧。）
- **不是时间不够**（别去调大 dwell）：2026-08-15 实测，少收的那些轮次 scroll 步花的墙钟**更长**
  （6.3–9.2s），够数的只用 3.2–4.7s。自变量是帧，不是时长。
- **修法：换成 render-independent 的取数，别去要帧。** 在页内调站点自己的请求客户端
  （`evaluate` step，Tier A），窗口显不显示都照跑——`douyin-search` 正是这么解决的（它是目前
  已知唯一吃这一格的站）。**别把 dwell 心跳加回来**：它依赖的那个帧本来就不受我们控制。

### 4.3.66 douyin 上稍长一点的 in-page eval 稳定回 `Detached while handling command.`

- **症状**：对 douyin 的页面跑一段十几秒的 `cdp_look` / `evaluate`（比如内嵌 `await sleep` 的探针），
  稳定报 `Detached while handling command.`；同样写法在 xhs 上没事。
- **意味着什么**：**别用长 in-page eval 去观察 douyin**，换成多次短读（每次几百毫秒内返回）。
- **别误判**：它不是采集逻辑坏了，也不是登录态问题；采集本身照常跑（recipe 里的 `evaluate` 都很短）。

### 4.3.67 反复吃风控挑战：先问这条 recipe 是不是**把关键词拼进 URL 直达**的
- **判据**：这个站点是搜索类、`entryUrl` 长得像 `https://站点/search/{keyword}?...`，而且挑战不是
  偶发而是**高频复现**（`challenge` 命中 → facility 冷却十几分钟 → 到点又撞）。
- **根因**：直达搜索结果页在站点眼里是一次**没有任何前置交互**的深链请求——真人到不了那个 URL，
  他得先在搜索框里打字。到达路径本身就是判据的一部分，登录态再真也补不上它。
- **修法**：走完整的人肉路径（点搜索框 → 打字 → 点搜索按钮 → 点筛选 tab），让页面自己导航过去。
  代价是慢（douyin 实测 30–40s vs 直达 7s），换来的是零验证码。两处配套别忘：
  ① 这条 recipe 多半会**超过并发扇出的默认成员闸**（25s），在 manifest 里申报
  `member_timeout_ms` 放宽自己那一格，别去抬全局；
  ② 页面壳可能因此换了一个（douyin 从 `/search` 落到 `/jingxuan/search`），凡是写死了
  **构建产物名字**的地方都会当场炸——`webpackChunk<xxx>` 这类全局名必须按语义扫（见
  `douyin-search.recipe.json` 的 `_why_semantic_module_scan`），别写死。
- **选筛选 tab 用站点自己的语义属性**（douyin 是 `#search-toolbar-container span[data-key="video"]`），
  别用压缩类名——后者一次重新构建就换。

### 4.3.7 一个 `expect` 报「某某选择器没出现」，其实是被站点拦下了
- **症状**：`step#N expect 未满足：<结果区选择器> 在 8000ms 内没有出现`。读起来像"选择器漂了"，
  于是人去改选择器——**方向正好反了**。
- **判据**：去看那一刻页面**是不是拦截页**。最快的一手是 `cdp_look` 打同一个 URL 读
  `location.href` + 一段 `innerText`（Google 会落在 `/sorry/index`、Brave 会显示「正在验证您不是
  机器人」）。**别看失败截图**：后台标签的截图常常是一张全白（合成器没画帧），证明不了任何事。
- **为什么会长成这样**：登录墙/拦截页的探测在 entry 那一刻做过一次，而拦截**多半是被动作引出来的**
  ——首页好好的，一发搜索才跳过去。runner 在失败路径上会补探两次，**顺序是先状态图、后 wall**
  （具体的先于笼统的）：
  1. **按状态图认一眼**。认出来的话结论是 `challenged`，reason 里带状态名（`cf/banned` 之类）。
     所以**报 `challenged` 且 reason 里有 `cf/...` 时，别去查 `loginCheck.wall`**——CF 那三档
     根本走不到 wall 那一步，改那儿的选择器是白改。
  2. 状态图认不出，才轮到 `loginCheck.wall`，认出来报 `needsLogin`。

  **还报成 expect 未满足**，说明两道都没认出来：状态图里没有这张页（今天只有 CF 三档，站点自己的
  拦截页不在其中），而且这个 facility 的 `loginCheck.wall` 也认不出它——去 recipe 里把 wall
  的选择器补上（这不是可选的润色：两道都认不出 = facility 的冷却不会触发，下一发继续去撞）。
- **撞了之后**：该 facility 进入冷却（`FacilityCooldown`：连着撞翻倍、跑成一次清零）。冷却期内的
  调用**7ms 就被拒**，回的是一句说得出"我在冷却、还剩多久、因为什么"的 `CoolingDownError`，
  不是一个空结果。看到它不用排查——那是闸门在正常工作。
- **退让多久不是写死的，是量出来的**：底数和封顶由 `data/block-episodes.json`（`BlockEpisodeLog`）
  按 facility 分别喂——撞墙开一条 episode，之后**又被拦**给下界、**跑成了**给上界并封口，靠自然
  流量（冷却到期本来就会放行一发）收窄区间，不刻意去探。学不到就退回 60s 起、封顶 30min。
  **底数取见过的最短一次成功等待**（低估会被翻倍自己纠回来，高估则是白罚站、没有信号能纠），
  **封顶由下界抬**（douyin 实测 3h10m 仍被挑战，30 分钟封顶就是在假装退让），硬顶 12h。
  排查时直接读那份文件：`spentLastHour` 那一列还顺带记着撞墙前一小时我们发了几发，是
  `perHour` 闸门该定在几的实测分布。

### 4.3.8 搜索腿全线被拦：先看是不是**出口 IP** 被打穿了
- **判据**：不是"某个站点不高兴"，而是**同一出口上好几个站一起翻脸**。2026-08-13 实测：连打约
  一百发之后 Google 稳定回 `/sorry/index`（换查询、单发都一样 ⇒ IP 级不是会话级），**同一出口上
  Brave 也跟着弹人机验证**，而百度毫无影响。
- **量到的余量**：18 发挤在 13s 内（≈80 次/分钟）两次里一次被拦 6 发；18 发拆成 3 轮 × 6 并发
  （≈35 次/分钟）两次都零被拦。**但累计量也算数**——单轮安全不代表连打一小时安全。
- **修法**：等（拦截是瞬时的，恢复后单发照常）+ 别再连打。**别调大 `expect` 的 timeout，也别改
  选择器**——那两样都不是病因。压测这类腿之前先想清楚：它和用户日常浏览共用一个出口 IP。

### 4.4 表单流程走一半就断：下一个控件"找不到"
- **症状**：`click` 报 miss，或 `expect` 超时说某个按钮没出现；页面看上去好好的。
- **真因**：**下一个控件要等上一个 resolve 了才渲染**（提交按钮要等挑战发 token；确认按钮要等
  一次网络往返）。"当场找不到"被当成了"不存在"。
- **修法**：用那一步的 **`expect`**（等它引发的结果出现），**别把等待焊到 `click` 的 timeout 上**
  ——等的不是自己那次点击。见 `authoring.md` §3.5。

### 4.5 点着了，但点的是别的东西
- **判据**：动作"成功"了，后果却完全不对（例：跑完发现用户被签退）。
- **真因**：`click` 点的是**第一个匹配**，而选择器不唯一。实测 `button[type=submit]` 在
  `console.groq.com/keys` 第一个命中的是「Sign Out」。
- **修法**：点按钮一律用 `data-testid` / 唯一 id，**别用类型或标签选择器**。

### 4.6 点了、看起来在转，转完回到原地（人机验证类控件）
- **判据**：手工点能过，recipe 点不过；重试更多次**反而全废**。
- **真因**：**在控件就绪之前点下去，会把它打进失败态**——早点不是白点。而"就绪没有"从 DOM 里
  看不出来（widget 在 closed shadow root 里，实测 DOM 连续 9.3 秒一个字节不动）。
- **修法**：那一步加 **`settle`**（等这块区域画完停住再动手，判据是"变过了 + 停住了"）。
  细节见 `human-verification.md` §3.5。

### 4.7 「动作发出去了」 ≠ 「动作有效果」——3.7 在写侧的镜像

- **症状**：一个动作反复不生效，而每一次投递都"成功"。于是你开始怀疑投递通道，一种一种换。
- **真因可能根本不在通道上**：**那个动作在当前状态下本来就什么都不做。**
- **实录（2026-09-08）**：清空 QQ 输入框，投退格删不掉——`WM_CHAR 0x08` 试过、`WM_KEYDOWN VK_BACK`
  试过、连投 60 次、跑 6 轮、换成真实合成输入，**一个字符都没少**。真因是**光标停在开头，退格是
  空操作**。先 `Ctrl+A` 全选再删，一次干净。四种投递方式验的全是"键到没到"，而错的是"这个键在
  这个状态下有没有事可做"。
- **判据**：动作不生效时，先问**"它在这个状态下该有什么效果"**，再问"它到没到"。两问顺序反了，
  就会像上面那样把六轮实验花在一个正确的通道上。
- **和 3.7 的关系**：3.7 是读侧（"没读到"被当成"读到了：没有"），这条是写侧（"发出去了"被当成
  "起作用了"）。**两者都表现为"我拿到了一个看起来有内容的答案"**，也都是更省事的那一句。

### 4.8 自己做对照实验时，最先骗到你的是自己的仪器

同一晚（2026-09-08）两次，都发生在**为了验证别的东西而临时写的探针上**：

- **探针的字形是被测系统的一部分。** 探针用了 `Zx9`，OCR 把 `9` 读成 `g`，于是"字确实进了输入框"
  被判成失败——**一个假阴性**，差点据此推翻一个正确的结论。选探针要挑识别层不会犹豫的字形。
- **上一轮的残留会伪造成功。** 跑"不按任何键"的对照组时没清输入框，读到的是上一轮留下的探针，
  于是**对照组"成功"了**。这个方向更危险：假阴性只是让你多查一轮，**假阳性会直接推翻正确结论**。
  对照组跑之前必须把现场清干净，而且**清干净这件事本身要回读确认**（见 4.7 那条：清理动作也可能
  是空操作）。
- **判据太松等于没有判据。** 焦点环里既有消息输入框也有搜索框，探针进了搜索框同样"看得见"——
  只按"看得见"判，就会把一次跑错地方读成成功。加上区域约束（`see.region` 存在的理由）才有牙。

### 4.9 「重试一下就好了」——先问它重的是哪一格

桌面这一面有个**介入闸**：一步的 `expect` 没兑现、而它的靶子是缓存给的（`template` 的图 /
`point` 的坐标 / `pinned` 的控件名），引擎会作废那个靶子，下一趟重走梯子重新定位。于是会出现
「昨天不行、今天好了」，而中间谁都没改过 recipe。

**这不是"它自己会修"，别据此放松判据。** 三件事必须分清：

- **它只作废 locator，从不碰判据。** 判据能被自动改，整套东西就退化成「模型自己说自己成了」。
  所以**如果你看到一条判据时好时坏，那是判据写松了，不是介入闸在起作用**——去查 `see.region`
  够不够紧、`not` 该不该加，别等它"自己好"。
- **它不会在同一趟里重来。** 这一趟已经点过一次，副作用可能已经发生（发消息那条链路上，重来
  就是发两遍）。所以"作废"的收益要下一趟才看得到；这一趟照样判 drift。
- **它作废的只有三档**：`template` / `point` / `pinned`。`screen` 和 `a11y` 是**现读**的，
  没兑现说明界面上真的没有那个东西——那时候该改的是 recipe，不是等谁来自愈。

**判法**：看那一步的 `seeVia`。写着 `screen` / `a11y` 的，介入闸压根没管它。

### 4.10 排查这条链路时"只剩一句 reason"
- **症状**：失败只有一行"X 没出现"，而 one-shot 的 tab 已经关了，现场没了。
- **现在有了**：失败会在释放 lease 之前抓现场——URL、可见文本（站点自己的报错几乎总在这里）、
  视口截图（落 `data/failures/`，路径进 DebugBox `channel:recipe`）、以及**失败那一步自己的观测**
  （settle 等了多久、点没点着，写在错误消息的「本步观测」里）。
- **先去看它，再动代码。**

## 边界 5 — 映射

### 5.1 换了读取方式之后字段全空
- **真因**：**`network` observer 读站点的原始 wire body（常 snake_case）；`evaluate` step 读站点 SDK
  转换后的形状（常 camelCase）。** 换一种，**每一条 dot-path 的大小写都变**。
- **修法**：**对着 live body 重新 capture**，别凭记忆改 dot-path。

### 5.2 `outcome=ok` 但 0 条
- **真因**：`dedupeBy` 填的是**映射后**的字段名。它是 **RAW item 的路径（映射之前）**。
- **修法**：填原始 body 里的路径。写错 → 每条都被当成"缺 id"丢掉 → **静默的 0 条 ok**。

## 边界 6 — 宿主

### 6.0 改了 recipe、重启了，活体行为还是老样子（`data/recipes/` 在遮蔽它）
- **判据**：改动确实进了 `packages/<facility>/<id>.recipe.json`、后端也重启了，跑出来却完全是旧行为
  ——旧的 step、旧的选择器、旧的 `visibility`。**没有任何报错**，因为跑的是另一份完全合法的 recipe。
- **真因**：recipe 是**两层挂载**：内置 `packages/`（仓库里那份）+ 用户 `data/recipes/`，
  **同一个全名由用户层胜出**（`mountRecipePackages`：`for (const layer of layers) recipes.set(...)`，
  后一层是 user）。全名 = `<npm 包名>/<局部名>`（见 `docs/PACKAGE.md` §1.1），所以**只有 npm 名
  相同的那两个包**才会互相盖——也就是说，能盖掉内置 xhs 的只有另一份 `@streamapp/xhs`。这一层
  本来是给"用户导入的分享包 / 官方包升级"用的，但它同样会把一份**你正在改的 builtin recipe**
  整个盖掉。迁移/改名/重构之后最容易撞上：`data/recipes/` 里躺着的是几个版本之前的快照。
- **修法**：`ls data/recipes/*/` 找 `package.json#name` 与你在改那个包相同的目录；有就删掉
  （或确认它才是你要的那份）。**看目录名不够**——目录名是包名把 `/` 换成 `__` 之后的样子。
- **通用教训**：**"改了没生效"要先问"我改的这份是不是正在被用的那份"**，再去怀疑热重载和缓存。
  凡是"内置 + 用户覆盖"的分层查找，覆盖层永远是第一个要排除的嫌疑。

### 6.1 重启之后必失败（后端根本没起来）
- **判据**：后端自己就是那扇门，**它没起来 = 8900 上没人听**——`curl 127.0.0.1:8900/api/health`
  直接 `Connection refused`，`pnpm dev` 的输出里能看到锁的拒绝原因。（自托管容器档前面有 Caddy，
  同一个故障在那里的形状是**502 且 body 为空**：应用层出错会回 JSON，空 body 只能是上游没应答。）
- **真因**：**pid 不能标识进程。** 重启后 pid 会复用（容器里尤甚，pid 命名空间每次重置），锁里
  记的 pid 很可能又活了，而且**正好是本次运行的启动器**（cmdline 里同样含 `serve.ts`）→ 锁误判
  "另一个实例在跑" → 拒绝启动。
- **修法**：锁里记 `<pid> <启动时间>`（`/proc/<pid>/stat` 字段 22），pid 复用时启动时间必然不同。
- **通用教训**：**错误的"形状"比错误的内容更能定位故障层。** 内容会骗人，形状不太会。
  另：**别把"起不来"误诊成"冷启动慢"**——这个误诊糊弄了好几轮。

### 6.1.5 `pluginTarget` 取址答空

- **判据**：频道 `plugin-target`（`data/debug-failures.jsonl`）。先看形状：
  - `not-awake`（standby 状态 `asleep`、容器 `stopped`、缓存 origin 为空）——**这是正确答案，不是
    缺陷**：容器睡着本就没有 loopback 口。08-24 起 777 条样本里 769 条是这个形状。
  - `standby-unbound`（8 条）——先看 `standby` 那一格是哪种 inert 原因；够不着 Docker 是一条独立的
    可通知缺陷（`docker-unreachable`，判据在 `pluginTargetNotifiableDefect`，见
    `src/plugins/target-miss.ts`），不是噪音。
  - `awake-without-origin`（醒着却取不到址）——**这才是要等的真缺陷形状**，跨三轮清点、10 天、
    零样本。见到再深挖。
- **已排除**：**Cell 缓存陈旧**——777 条样本里 0 条是 `awake-without-origin`，缓存 origin 与 inspect
  出的宿主口从没不一致过。别把这一格当嫌疑对象去查缓存失效。
- **已知非故障**：standby 状态为 `stopping` 的那一小段窗口里，容器还 `running`、缓存口与 inspect 口
  逐字一致，取址仍答空（6 条样本）——真实消费路径会等它停完再拉起来，**只是白等一会儿，不是故障**。

### 6.2 整个 facility 一条都采不到 / 每轮直接被跳过
- **判据**：日志/health 里是 `EnvironmentUnavailableError`（"跳过本轮"），**不是**源故障、不是 drift。
- **真因**：**采集浏览器不在**——用户的 Chrome 没开，或开着但扩展没连上中继。Stream 自己没有浏览器
  可以退回去（这是设计，不是缺陷），所以整条 lane 无事可做。
- **修法**：`ensureHarvestBrowser()` 会去唤起它；唤不起就问 `harvest_capability`（MCP，无参数；HTTP 同一个
  结构是 `POST /api/browser-capability/diagnose`）——`state` 直接告诉你是「装过但现在没连」
  （`disconnected`，叫醒扩展即可）还是「从没连上过」（`never-seen`，得先装），`chrome` 块里的
  `candidates` / `mustChoose` 说明该装/该选哪一侧的 chrome.exe。
  **判成"源坏了"是误诊**：把一个环境不可用误记成源故障，会把好源拉进退避黑名单。
- **⚠️ 不存在的一类故障**：`launchPersistentContext exitCode=21`、`SingletonLock` 陈旧锁、
  `data/browser-profiles/*`——Stream 不启动浏览器、不管任何 profile。见到指令让你 `rm SingletonLock`，
  删了也不解决任何问题。

### 6.3 capture / validate 跑不起来
- **真因**：以为浏览器在 backend 容器里。**反了**——`docker exec` 进去必然失败，那个镜像里**没有浏览器**。
- **修法**：在**宿主**上自己起一个带调试端口的 Chrome（非默认 user-data-dir，M136+ 拒绝在默认档上开这个口），
  然后在宿主上 `pnpm exec tsx …`：
  ```bash
  chrome --user-data-dir=/tmp/stream-chrome --remote-debugging-port=9333 &
  ```
  换端口就设 `STREAM_AUTHORING_CDP_URL`（默认 `http://127.0.0.1:9333`）。
  **调试端口是攻击面**：只绑 loopback、只在自己机器上开，别对局域网敞。
- **顺带**：`record login` / `record explore` 两个子命令**已删**——它们的全部意义是"坐在 Stream 自己的
  浏览器窗口前把 profile 登上"，而那个 profile 不存在了。登录就在用户自己的浏览器里登，和别的网站一样。

## 附录 A — 站点特化：xhs（小红书）

> 站点特化条目放这里，不要混进上面的通用层。新增站点新开一节。

- **单会话，硬不变量。** 这里的"单会话"是**站点的**限制：xhs 只允许一个登录会话在线，谁上线谁把
  对方挤掉。约束来自**站点**，不来自采集这一侧。
  **正因为只能有一个会话，采集就该直接用用户那个浏览器的登录**，而不是另养一个跟它抢的
  （理由见 spec `2026-07-28-xhs-harvest-on-user-chrome-design.md`）。所以"抢会话"这类故障的来源
  只有一个——**你自己另开了一个 xhs 登录**（另一台机器、另一个 profile、无痕窗口）。
- **首屏 SSR。** feed 的第一批笔记 SSR 进 `__INITIAL_STATE__`，**不发 XHR**；要滚动之后才有接口可拦。
  只挂 network observer 会丢掉第一批（→ 3.1）。搜索面绕开了这个坑，靠的是 runner 在 observer 挂好
  之后**强制重走一次 `goto`**（`recipe-runner` 的 `capturesLoad`），于是带 keyword 的首屏那次
  `/api/sns/web/v1/search/notes` 也被看见——**这是时序修法，不是"搜索页没有 SSR"**，别推广成后者。
- **back-nav 会重拉推荐。** 从笔记页 back 回 feed，站点可能重新拉一批推荐 → **账本作废**。
  所以 fallback-nav 有雪崩效应（→ `pipeline.md` §4）。
- **detail 读笔记页的 `__INITIAL_STATE__.note.noteDetailMap`，不是 feed API**（后者抽走了视频 masterUrl）。
  字段是**小驼峰**。
- **feed 卡片留在 DOM 里**（不是严格虚拟列表）——所以定位可以直接读目标 anchor 的坐标（→ `pipeline.md` §3 第一档）。
- **一张卡带 3 个同 id 的 anchor**，且**文档序第一个是隐藏的**（2026-07-28 搜索结果页活体量的：
  `/explore/<id>` 是 `display:none`、rect 全 0、**中心点算出来是 (0,0)**；后两个是
  `/search_result/<id>` 的封面 262×350 和标题行 238×39）。所以点击必须过"看得见"这道判据，
  读视口必须**按 id 去重 + 先判可见再记 id**（否则隐藏的那个先占住 id，真卡被自己的影子挤掉）。
  判据在 `src/replay/card-id.ts` 的 `VISIBLE_EL_FN_SOURCE`（盒子非空 + 非 `visibility:hidden`）。
- **不要连点。** 打开 detail 走"滚到卡片 → 可信点击 → in-feed 浮层"，不是快速连续导航——会触发风控。
