# 怎么观察：建立可观察性的方法

这条链路横跨"浏览器里发生的事"和"后端认为发生的事"。**几乎所有难 bug 都是这两者不一致，
而不是任何一边自己坏了。** 所以观察的核心不是"多打日志"，是**在边界上把两边的量放在一起比**。

---

## 1. 观察四律

### 律一：别估一个系统能直接告诉你的东西

写"估算 / 推断 / 启发式"之前，先问一句：**这个值有没有权威来源？**

> 实例：为了把卡片滚进视口，花了好几轮做"按账本 index 最小二乘拟合坐标"的外推——
> 而 DOM 里就存着那张卡的 anchor，带着真实 `boundingRect`。**一次查询的事。**

推论：**能读就别猜。** 包括"我有没有办法看"这件事本身也要先去查（这次的教训是：Playwright 的全部原语
一直在手边，我却在用重启+日志做二分猜测）。

### 律二：探针要打在两个世界的交集上，不是各自的量

任何单独一个数字都毙不掉猜想，**交集才行**。

> 实例：一行日志 `vp=20 known=0` —— *页面上有 20 张卡 / 其中 0 张是我们认识的*。
> 它一次性毙掉了"滚轮是 no-op"、"选择器传错了"、"tab 被关了"三个猜想，
> 并直接指出真因：**账本和 DOM 是两批不同的内容。**

设计探针时问自己：**这一行能不能同时报出"页面侧的量"和"后端侧的量"，并让它们当场对上？**
不能，就重新设计这行日志。

### 律三："空"和"没变化"是状态，不是结论

异步渲染的页面：重渲染期间读到 0 张卡是常态；读到和上次一样的卡，可能只是还没渲染完，不是"没滚动"。
**把瞬时读数当判决，在最终一致的系统里必错。** 要么容忍几轮，要么等一个明确的就绪信号。

### 律四：工具的读回不等于真相——要在生效的那一侧量

律一的反面。律一说"能读就别猜"；律四说**读到了也未必是真的**：一个库的读回反映的是**它自己的模型**，
不一定是运行时的真实语义。抽象泄漏的地方，读回就会撒谎——而且**理直气壮地撒谎**，比没有读数更危险。

> 实例：`ctx.cookies('https://pan.quark.cn')` 报告 25 个 cookie 全部"对该 URL 可见"，`__puus` 赫然在列。
> 但 Playwright 的这个过滤器**不模拟 host-only 作用域**：那些 cookie 注入时没带前导点，Chromium 根本
> 不会发给子域。页面里 `document.cookie` **一个登录 cookie 都没有**，接口回 `401 require login [guest]`。
> 这个假读数骗掉整整一轮诊断，还差点把"我注入错了"误判成"这站会话短命、cookie 注入不适用、得改扫码"。

**推论一**：判据要落在**消费者**那一侧——页面的 `document.cookie`、一次真实请求的返回、站点自己的接口
说你是谁。生产者(我注入了)和中间层(库说它在)的自述都不算数。**渲染也算中间层**:SPA 带着有效 cookie
也可能因别的原因被弹回落地页,"看着像没登录"不等于没登录。

**推论二(归因纪律)**:**有反例在,就别归因于"外部条件不行",先怀疑自己。** 上面那轮里,用户一句
"AList 只用 cookie 就登录着"直接证伪了"夸克会话短命"这个结论——**一个能用的反例胜过一整轮推理。**

## 2. 配套纪律：先给自己一条机器可读的验收判据

动手改之前，**先写下"改成了"长什么样**，而且必须是**机器可读的一行**。

> 实例：`step#0 open` 必须是 `locate+click`，不是 `fallback-nav`。

有了它，每一处改动都要能回答"它怎么让这行日志变过来"。**没有判据的"大面积修改"会退化成凭感觉重构**——
这是被用户当场叫停过的真实事故。

## 3. 手头有什么观察手段

按成本从低到高：

| 手段 | 看什么 | 备注 |
|---|---|---|
| **`[recipe-probe]` 日志** | 每阶段墙钟 + 滚动曲线 + 自定义 detail 行 | `probe.mark(phase)` / `probe.detail(line)`；`RECIPE_PROBE=0` 静音。**默认手段。**（**没有浏览器内存这一项**：标签在用户自己的 Chrome 里，后端侧扫 `/proc` 只会稳定报 0——**测错进程比不测更坏**。） |
| **采集曲线 `items a,b,c`** | 每次滚动后的累计条数 | **第一次滚动前是 0 = 首屏没有 XHR（SSR）**。这一个数字就能定性 |
| **outcome.timing** | 各阶段耗时 | 找"慢在哪一段" |
| **抓包（`capturing.md`）** | 页面自己发的那个请求：url / method / body / 完整回包 | **两种形态**：只装了 npm 包走 `cdp_*` 三步（拦截器要和开页面同一次调用）；有源码检出还可以用 `scripts/recipe-capture.ts` 把完整 body 落盘（控制台预览截断在 400 字符）。DOM 结构同理（`recipe-dom-capture.ts` / `cdp_look({inventory:true})`） |
| **`cdp_look` / `cdp_shot` / `cdp_act`（`target: 'facility:<facility>'`）** | 正在跑的那个 tab：eval / 截图 / 真点一下试试 | 一等工具，秒级替掉"改代码+重启"的猜测循环。见 `drive-live-ui` skill |
| **`POST /api/sources/preview`** | 这个 source **现在**真去采一遍会得到什么 | **验"采到了没"只能用它**，见下面 §3.5 |
| **`recipe_debug_start` / `_next` / `_abort`（MCP，桌面 recipe）** | 同一趟真实运行，**每一步之前停下来**：停着时用 `cdp_shot`/`cdp_look`（`target:'app:<进程>/<标题>'`）看屏幕，`probes` 里是这一步走了哪条识别路、branch 成没成立、每次读屏多少毫秒 | 走的是 runner 本身（只是多一道闸），不是模拟——放行的那一步真的会做（发消息就真发）。停着的会话占着桌面会话租约，十分钟没人放行自动中止；不继续就 `abort`。有它就不用"改一行、整跑一遍、看日志猜"了 |
| **`data/debug-failures.jsonl`** | 历史上每一条 `ok:false` 的 DebugBox 条目（全频道，一行一条 JSON，最旧在上） | **要"等撞一次现场"就只看它。** `GET /api/debug/log` 读的那个环是 200 条、跨全频道共用、**进程一重启就清空**——热重载一天几十次，凭它等偶发故障永远等不到。超 4MB 轮转成 `.jsonl.1`，只留一代。一字不差的重复按 10 分钟折叠，**带 `_repeated` 的行是常态噪音、不是现场**。读：`grep '"ext-cdp"' data/debug-failures.jsonl \| tail` |

## 3.5 判"采集成功了"之前，先排除**命中缓存**

改完一份 recipe 想验它，最顺手的是 `POST /api/streams/:id/refresh`。**它会骗你**：refresh 虽然是一次真实
tick，但**吃 cadence TTL 缓存**——上一轮的结果还在新鲜窗口里，这一次直接把旧内容还给你，`fetched` 有数、
条目齐全，看着完全像"采到了"。而浏览器**这一轮根本没被碰过**，你改的东西一个字节都没跑。

- **判据**：harvest 账本里那行 summary 带 **「命中缓存」**（DebugBox `channel:harvest`；后端就是照
  `t.cacheHit` 拼的这四个字）。看到它，这一轮的所有数字都不能用来判对错——包括"条数对不对"。
- **要 fresh 就用 `POST /api/sources/preview`**（body `{ sourceId, params }`）：它内部走
  `readSourceNormalized(..., { fresh: true })`，**跳过缓存命中检查**，每次都真去采一遍；而且**不落库**
  （不写 store、不进 dedup、不记 health），所以拿它反复验不会污染任何东西。
- **通用教训**：**"有数据返回"不等于"这一轮真的跑了"。** 任何带缓存的验证路径，先找到"这次是不是真跑了"
  的那个字段（这里是 `cacheHit`），再去看数字。顺序反了，你会拿着上一版的输出宣布新版好了。

## 4. 加探针的两个套路

**套路 A —— 交集行。** 一行同时报页面侧和后端侧，且当场比对：
```
locate: step=0 y=1001 vp=17 known=0        ← 视口有 17 张 / 认识 0 张
locate: step=0 y=1001 vp=17 inDom docY=3228 ← 目标卡在 DOM 里，坐标 3228
locate: found idx=0 after 1 jump(s) + 0 wheel(s)
```

**套路 B —— 决策行。** 把"走了哪条分支"打出来，尤其是**降级分支**：
```
step#0 open locate+click     ← 正常
step#0 open fallback-nav     ← 降级了！但它能出数据，所以不会报错
```
**能出数据的降级路径是最阴险的故障**——指标绿着，能力早没了。**所有降级分支都必须打点。**

## 5. 判"是不是 bug"：对照实验最便宜

同一输入、两条路径，几分钟就能区分"我们坏了"和"数据本来如此"。

> 实例：detail 拿到 `comments=0`，差点当 bug 修。把同一条笔记换另一条路径（独立的笔记页）打开，
> 还是 0 → **这条笔记本来就没评论。** 省掉一整轮瞎改。

## 5.5 detail 打开的 probe 分段：humanize vs 等待，别把 humanize 当性能问题

`locate` 步的墙钟拆成三段，各一行 probe（也进 DebugBox `recipe` 频道），后面紧跟 observer 的 `state-wait`：

```
step#0 locate      找卡（账本跳/滚；卡通常在 DOM 里，一步跳到，~几十 ms）
step#0 humanize    拟人点击本身：光标一小步一小步挪到卡上 + 按下松开（noWaitAfter，不含等页面变）
step#0 open <via>  OBSERVE —— 等 note 真打开（url 出现 noteId）；locate+click=开成、fallback-nav=降级
step#0 state-wait  observer 轮询到 readyWhen 为真（见下，这里没有固定 dwell）
```

**慢在 humanize 是设计，不是 bug，也别去"优化"它**：把插值光标轨迹压成一步 = 点击变假 = 惹风控
（xhs 已多次把我们墙成 300031）。曾差点用 `force` 点击去砍它，spike 当场拦下——**先量哪一段慢，
再决定动不动**。**这条链路上的耗时数字一律现场量**（probe 每次运行都在打这四行），别从任何文档里
照抄——采集实现变一次，抄来的数就废一次。

`open` 之后**没有固定盲等**：直接进 observer 的 `state-wait`。（别和 `step#N settle` 搞混：那是
recipe **自己声明** `settle` 才有的一行，跑在这一步**动手之前**、是真闸门；没声明就一行都没有。）
"`readyWhen` 可能选到一个恒真字段、所以要盲等一下"这个推理**是错的**，别照它加盲等：

> **实测（2026-07-27，真浏览器，trusted click 打开笔记，每 10ms 采样
> `__INITIAL_STATE__.note.noteDetailMap[noteId]`）** —— 量的是**站点自己**往 state 里填数据的顺序，
> 和用哪个浏览器无关，所以换到用户自己的 Chrome 之后这组数字照样成立。
>
> 视频笔记（`type:'video'`）**分三阶段**填，不是原子出现：
>
> | t | `note` key 数 | `note.desc` | `note.video.media.stream` | `comments.firstRequestFinish` | 评论数 |
> |---|---|---|---|---|---|
> | 1ms | 6 | ❌ | ❌ | **false** | 0 |
> | 148ms | 15 | ✅ | ✅ | **false** | 0 |
> | 355ms | 15 | ✅ | ✅ | **true** | 10 |
>
> 图文笔记（`type:'normal'`）：条目**原子出现**——第一帧就是 14 个 key、标题/正文/作者/图片齐全、
> `firstRequestFinish` 已经 true、评论 10 条；10ms 采样抓不到任何中间态。

结论：`comments.firstRequestFinish` **不是恒真**，它是**最后一个就绪的信号**（晚于内容填完的 148ms），
所以恰恰是最严格的 gate——**别去换掉它**。observer 自己的 poll-until-`readyWhen` + `maxWaitMs` 就够
（`maxWaitMs` 是**两次读之间**才检查的，所以单次 `readState` 另有自己的上限，否则一次挂住的读就把它
架空——见 `failure-atlas.md` §3.4）：
读到半成品判 not-ready 会继续 poll，而 `observer-pipeline.ts` 的 `identity` 过滤会把 map 里那个恒存在的
`undefined` 占位条目排掉，占位不会被误当就绪。真正卡时间的是 `pollMs`——原来 250 会把 355ms 的就绪时刻
推到 500ms 的 poll 边界，已改成 **50**（`packages/xhs/xhs-detail.recipe.json`）。

## 6. 反模式（都真实发生过）

- ❌ **把"慢"当性能问题优化。** 先问"它是不是在做本来不该做的事"。**反例正是上面的 humanize**：
  它的"慢"是刻意的反检测，砍了就露馅——所以**先 spike 出是哪一段慢**（见 §5.5），别一看总数大就动手。
- ❌ **靠"改代码 + 重启"做二分猜测。** 每轮一分半，还只能看见预埋的数字。加探针 / 开读口，别猜。
- ❌ **裸 curl 一个签名/登录态的接口"看看返回形状"。** 拿到的是挑战页，不是 body——那正是它需要浏览器的原因。
- ❌ **换了读取方式却不重新 capture。** `network` observer 读的是**站点原始 wire body**（常是 snake_case），
  `evaluate` step 读的是**站点 SDK 转换后**的形状（常是 camelCase）。**换一种就要重算每一条 dot-path。**
- ❌ **为了看一眼页面，另起一个浏览器 / 开第二个登录会话。** 单会话站点会把其中一个踢下线——而现在采集
  骑的就是**用户自己那个**登录，踢掉的会是他本人。要看就用 `cdp_look`（`target:'facility:<facility>'`）
  对着采集正在跑的那个 tab 看。
- ❌ **拿 `refresh` 的返回当"采到了"的证据。** 它吃缓存（→ §3.5），验一定用 `POST /api/sources/preview`。
