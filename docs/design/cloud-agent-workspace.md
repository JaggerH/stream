# 云端员工：Stream 作为 personal agent 的目标架构

> 决策记录，来自 2026-10-23 的产品化讨论。记录的是**目标形态**和已经拍板的决策，不是实施计划；
> 实施会拆成若干 openspec change。触发频率与容量一节**待讨论**，留了位置。
>
> 读这份文档时先放下「Stream = 定时采集 + recipe 重放」的现状框架：采集、Intent、网盘追更这些现有
> 能力在这里只是**员工可调用的工具**或**触发器的事件来源**，怎么接进来后面再定（见「与现有能力的关系」）。

## 一句话

用户在云端有一个**工作区**，里面有他自己、可能还有别的真人，以及他雇的若干**员工**。每个员工是一条长期
存在的对话：用户像派活给员工一样跟它说话；员工可以被定时、被事件、被同事叫醒，叫醒后在同一条对话里接着干；
员工之间可以互相派活、拉群围绕一个目标协作。脑子、对话、harness、工具调用全部在云端，手机端和桌面端只负责
显示；桌面端在线时，还把这台电脑的浏览器与桌面能力挂给云端的员工用。

## 目标模型

### 角色与对象

| 对象 | 是什么 |
|---|---|
| **工作区** | 一组真人 + 他们的员工 + 群 + 目标。个人用户 = 只有一个真人的工作区。上限 300 个成员（真人与员工都算）。 |
| **真人** | 工作区里的人类成员。拥有员工、发起对话、处理审批。 |
| **员工** | 一个 agent 成员：职责说明、负责的任务类型、技能、工具授权、风险放行规则、长期记忆。**由真人创建**，或由主对话按真人的要求创建。 |
| **主对话** | 每个真人有一条。它本身是一个特殊员工，除了干活，还能按要求建员工、调整员工、给员工派活。 |
| **对话** | 三种：真人与员工的私聊、群（若干员工 + 若干真人）、主对话。每条对话是一份追加写的事件日志。 |
| **目标与任务** | 群围绕一个目标展开；目标下有任务，员工可以认领、补充信息、交付。 |
| **触发器** | 挂在员工身上，到点或事件发生时叫醒它，在指定的对话里干一轮。 |
| **端** | 手机端、桌面端。都只是显示与操作的入口；桌面端（以及将来的安卓端）同时是能力的提供者。 |

### 已确认的行为

- **触发器叫醒后，接着同一条对话往下跑**，不另开子线程。
- **员工之间可以互相派活**；可以**拉群**，让多个员工围绕同一个目标补充各自知道的信息、认领任务。
- **员工是一个人**：它出现在私聊和多个群里，但只有一份记忆，所有对话里的轮次按员工排队执行，它在不同对话里说的话不会互相矛盾。
- **干活的过程多端同时看到**：模型的输出、工具调用、工具结果、状态变化，手机和电脑实时同步。内容都在云端，端只是收取。
- **审批卡在风险条件上**；审批是对话里的一条事件，所有端都看得到，在哪一端处理都行。
- **桌面端在线时，员工就能用桌面端的能力**（浏览器、desktop agent）；离线时这些能力不可用。
- 群里**可能拉进别的真人**，没最终定，但架构按「会」来留位置（见 D2）。

## 架构总览

```
 手机端（看、操作）               桌面端（看、操作 + 挂上本机能力：浏览器节点 / desktop agent）
        │                                      │  （能力连接只出站，凭证留在本机）
        └──────── 实时网关：按工作区推事件流，断线按序号续传 ────────┘
                                   │
 ┌────────────────────────── 工作区单元（一个工作区的全部状态）──────────────────────────┐
 │  对话服务      私聊 / 群 / 主对话；每条对话一份带序号的事件日志                          │
 │  成员          真人、员工（职责、技能、工具授权、放行规则、记忆）                        │
 │  目标与任务板  群的共同目标、任务、认领关系                                             │
 │  员工运行时    每个员工一个信箱；按轮执行、不持状态；挂起与恢复（审批、设备上线、慢工具）   │
 │  触发器        定时 / 事件 / 消息 / @提及 / 被派活 / 设备上线 → 往员工信箱投一条          │
 │  风险与审批    工具调用按风险条件判定 → 生成审批事件 → 挂起这一轮                        │
 │  能力在线表    工作区里哪些设备在线、各有哪些能力与身份                                   │
 │  记忆          真人记忆、员工记忆；世界知识按需检索                                       │
 └──────────────────────────────────────────────────────────────────────────────────┘
                                   │
   共享服务：模型网关（限流、配额、计费、缓存） · 外部工具连接器 · 外包沙箱池（写代码的子任务）
```

## 决策

### D1. 脑子在云端，端只显示

对话、员工、harness、工具调用、记忆全部在云端。端不持有任何权威状态，只订阅事件流、发送用户操作。
同一个工作区在任何端看到的内容一致，换设备不需要同步。

**为什么**：多端一致只有在「唯一的权威在云端」时才不需要同步协议；员工要在用户不在线时继续干活，
脑子也只能在一个始终在线的地方。

### D2. 单元 = 工作区

集群里的调度单位是**工作区**，不是用户：一个工作区的全部状态（对话日志、员工、任务板、触发器、审批、记忆）
落在同一个单元里，单元在某个时刻只在一个节点上活跃。网关维护「工作区 → 节点」的映射。

- 工作区内部的一切协作（派活、群、任务认领、审批决定、员工信箱）都是单元内的本地操作，用本地事务，不需要分布式锁。
- 一个工作区的规模（≤ 300 成员）一台机器扛得住；集群的作用是**放更多工作区**，不是把一个工作区拆开。
- 闲置的工作区可以卸载到对象存储，有触发器到点或有人打开时再加载。全局只保留一张「每个工作区下一次该醒的时刻」索引。
- **所有数据从第一天起带工作区 id**：每张表、每个对象存储路径、每条日志、每个缓存 key。不能有进程级的全局单例。

**为什么不是「一个用户一个单元」**：之前的讨论推荐过按用户切，理由是 personal agent 的数据天然按人切开。
但群里可能拉进别的真人，按人切开后跨人的群就要跨单元，单元架构最大的好处（协作不出单元）就没了。
按工作区切，个人用户与团队是同一个模型。

**留下的开放项**：两个**不同工作区**的真人要在一个群里协作，目前不支持。真要支持时，做成「共享空间」——一个
独立的、只放那个群的小工作区，双方以成员身份加入——而不是让群跨单元。

### D3. 员工 = actor

- 每个员工一个**信箱**。它在所有对话里的触发都投进这个信箱：真人的私聊消息、群里 @ 它、被派活、任务被分给它、定时、
  事件、设备上线。
- **同一时刻只处理一轮**；记忆只有一份。
- 出队优先级：真人在私聊里找它 > 群里 @ 它、派给它的活 > 定时与事件触发。同级先进先出。
- **挂起而不是阻塞**：一轮里要等审批、等设备上线、等一个很慢的工具时，这一轮的状态写进库、信箱让出，员工去处理别的对话。
  等的东西到了，作为一条新消息排回信箱，从挂起点继续。
- 员工对外有状态：在哪个对话里忙、排着几件、挂起着几件在等什么。群里的成员能看到。

**为什么不是「每个对话一个分身」**：分身之间记忆不同步，员工在群里答应的事私聊里不知道，用户感受到的是好几个人。
代价是忙碌的员工在多个对话间排队；挂起机制让「卡在等待上」不会让它在所有对话里失联。

### D4. 对话 = 带序号的事件日志

- 每条对话一份追加写的日志，每条事件带单调递增的序号。事件类型：消息（真人 / 员工）、员工的工具调用与结果、状态变化
  （开始一轮、挂起、恢复、结束）、审批请求与决定、任务的认领与交付、触发记录（是哪个触发器叫醒的）。
- 端订阅对话，从自己看过的序号往后收；断线重连按序号续传。
- **模型逐字输出的片段只推送、不落库**，落库的是完整消息。这样日志不随打字膨胀，回看历史与实时观看看到的内容一致。
- 日志永远保留原文。喂给模型的上下文是另外拼装的（D7），压缩不改日志。

### D5. 触发器

- 触发器属于员工，指向一条对话（缺省是员工与它主人的私聊）。触发时往员工信箱投一条「触发」消息，并在对话日志里记一笔，
  所以用户在对话里能看到「08:00 定时：查看今天的日程」这样的来龙去脉。
- 类型：定时、事件（外部 webhook、工具产生的事件、别的员工的交付）、设备上线（D8）、截止时间到。
- 可靠性沿用调度中心已有的做法：错过的触发补跑或合并、同一触发在飞时不重复投递、失败按策略处置。
- 触发频率、扇出、预算**待讨论**（见「容量」）。

### D6. 风险与审批

- **风险来自工具调用**，由三部分决定：
  1. 工具声明的副作用类型：只读 / 可撤销 / 对外发布 / 花钱 / 删除 / 凭证。（`cdp_act` 的 `intent: send | publish | purchase | delete | credential` 是现成的雏形。）
  2. 参数：金额超过阈值、对象是陌生人、批量操作。
  3. 执行身份与环境：例如工作身份下的一切对外动作（与 browser-identity 的「环境」对接）。
- 员工可以有放行规则（「这个员工发小红书不用问我」），由真人设置，主对话可以按要求替真人改，但改动本身是一次需要真人确认的操作。
- 命中审批的工具调用：生成一条审批事件写进**所在对话**，同时汇总到真人的收件箱视图；这一轮挂起（D3）。
- **审批在所有端一样**，看到就能处理。决定写进日志是原子的，先到的生效，后到的看到「已由某某处理」。推送只是提醒，不是审批通道。
- 审批有过期时间；过期视为拒绝，员工在对话里说明。

### D7. harness 自研、按轮无状态；ACP 只做外包工具

- 员工的每一轮：从库里读出员工配置、对话状态、记忆 → 拼装上下文 → 调模型 → 执行工具（经风险判定）→ 写回事件 →
  决定继续下一步、挂起，还是结束这一轮。任意一个 worker 都能执行任意员工的一轮，执行完不留状态。
- **上下文按轮拼装**，不重放整段历史：职责说明 + 员工长期记忆 + 本对话最近若干轮原文 + 更早部分的摘要 + 这一轮的触发事件 +
  按需检索到的旧内容与世界知识。
- 防跑飞：每轮的步数、token、时长上限；每个目标、每条派活链的预算与跳数上限。沿用 `src/intervention` 的三道闸与看门狗思路。
- **ACP 不做员工的 harness**：ACP agent 是一个会话一个重进程（数百 MB、秒级冷启动），工作区里大多数员工大多数时间闲着，
  员工必须是「一行数据」而不是「一个进程」。ACP 只作为员工手里的一个**外包工具**：遇到真正要写代码的子任务（代码包、自建后端、
  RSSHub 路由），交给一个编码 agent，跑在云端的临时沙箱里，或跑在真人自己的桌面端上（用他自己的订阅），结果交回员工。

### D8. 端是能力的提供者；能力在线表与动态工具

- 桌面端在线时，把本机能力挂到云端：浏览器节点（按 profile 与身份区分，见 `openspec/changes/browser-identity`）、desktop agent
  （窗口、文件、拉起应用）。连接只从端往外连，凭证留在本机。将来的安卓端同理。
- 工作区单元维护一张**能力在线表**：哪台设备在线、有哪些能力、哪些身份。
- 员工每一轮开始时，按「员工的工具授权 ∩ 此刻在线的能力」决定给模型哪些工具。离线能力的工具不给，或标为离线，免得模型规划到一半才发现用不了。
- 一轮中途需要的能力离线：员工在对话里说明，挂起这一轮，并给自己挂一个「设备上线」触发器，带截止时间。到点仍未上线就通知真人。
  云端无法替用户唤醒设备，系统只负责「等得住、说得清」。
- **产品形态**：桌面端是**一个应用**，同时包含对话界面、主机代理（desktop agent）、浏览器扩展的配对与管理。用户装一个应用、登录一次，
  这台电脑的能力就挂上去了。

### D9. 记忆三层

- **关于真人**：明确告诉过的事实、从行为推断的偏好。能看、能改、能删。
- **关于员工**：它自己积累的工作记忆（「这个号的发帖规律」「上次这个任务卡在哪」）。员工是一个人，所以这一层跨它所在的全部对话共享。
- **世界**：已有的条目、dossier、转写稿等，按需检索，不重建。

记忆的写入是员工的一个工具调用，所以会出现在对话日志里，真人知道它记住了什么。

### D10. 模型网关

工作区单元不直接调模型。共享的模型网关负责：全局并发与上游速率限制、按工作区与员工的配额、计量计费、按稳定前缀的 prompt 缓存、
失败换供应商（现有模型梯子的职责上移到这里）。吞吐的上限在这里，不在单元的 CPU。

## 容量

- **已定**：一个工作区 ≤ 300 成员（真人 + 员工）。一个工作区一台机器足够；同时在跑的轮次现实中是几十个量级，时间主要花在等模型。
- **待讨论**：触发频率与扇出。需要逐项定下来，才能算模型网关的容量与成本：
  - 定时触发的最小间隔；
  - 事件源有哪些、每小时多少条；
  - 一个事件叫醒几个员工（群里的扇出规则）；
  - 派活链深度上限；
  - 每轮的 token 预算；
  - 是否有集中的高峰（如开盘时段）。

## 与现有能力的关系

| 现有 | 在目标形态里 |
|---|---|
| MCP 工具目录 | 员工的工具来源之一，按员工授权与在线能力过滤 |
| 设备执行、浏览器节点与身份（device-execution、browser-identity） | 桌面端挂给云端的能力，原样延续 |
| `src/intervention` 的闸、审批、运行记录、看门狗 | harness 的防跑飞与审批机制的起点 |
| 调度中心 | 触发器的可靠性机制（补跑、互斥、失败处置）来源；采集任务本身以后作为触发器或工具接入 |
| 模型梯子、用量记录 | 上移为模型网关 |
| Intent（目标、判断标准、dossier） | 可视为一种只读型「研究员」员工的雏形 |
| 采集、网盘追更、购买决策等 | 员工可调用的工具，或触发器的事件来源，接入方式后定 |
| 管理面板 | 退到设置页；主界面换成员工列表、对话、收件箱 |

## 差距

| 层 | 现状 | 要做 |
|---|---|---|
| 对话服务 | 没有，对话一直借宿主（DSH、Claude Code） | 从零做：事件日志、序号、订阅 |
| 员工与主对话 | 没有 | 员工实体、信箱、主对话的建员工能力 |
| 员工运行时 | `intervention` 有闸与审批，但循环外包给 ACP 进程、一次任务一个会话 | 自研按轮无状态的 harness，挂起与恢复 |
| 群、目标、任务板 | 没有 | 群对话、@ 唤醒规则、原子认领 |
| 触发器 | 调度中心只触发确定性动作 | 新的触发目标「叫醒员工」，加设备上线触发 |
| 风险审批 | 有修 recipe 用的审批；`cdp_act` 有 intent 雏形 | 工具副作用声明、风险规则、放行规则、审批事件 |
| 能力在线表与动态工具 | 在线信息只在单进程内存里 | 工作区级的在线表、按轮过滤工具 |
| 记忆 | 只有「世界」一层 | 真人记忆、员工记忆 |
| 实时网关 | 面板用 ws 推少量状态 | 按工作区推对话事件流、续传 |
| 模型网关 | 进程内的梯子 | 共享服务 |
| 多租户 | 单进程单用户 | 工作区 id 贯穿全部数据，工作区单元、路由、卸载与唤醒 |
| 端 | 面板嵌在 DSH；desktop agent 与扩展分开装 | 桌面应用（对话 + 主机代理 + 扩展管理）、手机应用 |

## 拆分建议

按「每一步都能用」排，每一步拆成独立的 openspec change：

1. **单工作区跑通对话与员工**：对话服务、员工、自研 harness、实时网关、一个 web 端。工具直接用现有 MCP 工具目录。先在单节点、
   单工作区上跑，但数据从第一天带工作区 id。
2. **触发器与审批**：员工的定时与事件触发、风险规则、审批事件、挂起与恢复。
3. **桌面能力**：能力在线表、动态工具、设备上线触发；接上 browser-identity 的节点与身份。
4. **群与协作**：群对话、@ 唤醒、派活、目标与任务板、预算与跳数上限。
5. **端的产品化**：桌面应用（对话 + 主机代理 + 扩展管理）、手机应用。
6. **多工作区与集群**：工作区单元的路由、卸载与唤醒、模型网关服务化。

## 未定

- 触发频率、扇出与预算（见「容量」）。
- 跨工作区的真人协作（D2 的「共享空间」只是留位，未设计）。
- 外包沙箱的默认位置：云端沙箱池，还是优先真人的桌面端。
- 计费模型：模型费用由谁承担、按工作区还是按员工计。
